# Egress 与 VPN 共存方案

让虚拟机访问内网的流量也经过 Egress 的七层处理（凭证注入等），同时保留每台虚拟机独立的内网 IP。

带架构图的完整方案文档见 [docs/design.md](docs/design.md)。

在它之上怎么去掉单点、支撑大量虚拟机接入的设计草案见 [docs/ha-scale-design.md](docs/ha-scale-design.md)。其中一部分已经在实验里做过，结果见 [docs/ha-scale-results.md](docs/ha-scale-results.md)（第一轮：分片、多单元、两种数据面）和 [docs/ha-scale-results-2.md](docs/ha-scale-results-2.md)（第二轮：断电以外的故障、凭证的规模化、多台 VPN 服务器、经企业出口、逐台阻断）；控制面等部分仍然没有验证。

本方案和服务网格、出口网关等业界做法的逐项对照见 [docs/industry-comparison.md](docs/industry-comparison.md)。

> **状态：设计稿，未在生产环境运行过。** 地址均为示例。
>
> 已验证：整套方案在 EVE-NG 实验环境里用真实的 WireGuard 和 Envoy（1.40.2）跑通，包括复现现状、迁移、回退、TLS、主备切换，以及“虚拟机拿不到凭证”和各类凭证（客户端证书、令牌、静态凭证）分别能做到什么，见 [lab/eve-ng/README.md](lab/eve-ng/README.md)。此前还在本机用网络命名空间做过模拟（见"本地模拟测试"）。
> 未验证：真实的 Egress。实验和模拟里的 Egress 都是按"透明劫持"假设写的参考实现；性能和容量也没有测过。

## 问题

- 所有虚拟机的出口流量经过共享的 Egress 服务。凭证、身份等非业务逻辑在 Egress 内实现，虚拟机内的恶意进程拿不到。
- 虚拟机还要通过 VPN 访问内网。VPN 客户端运行在虚拟机里，流量离开虚拟机时已被隧道加密封装，Egress 只能看到密文，无法做七层处理。
- 结果是二选一：走 VPN 就得不到 Egress 的保护，不走 VPN 就到不了内网。

根源是封装的位置不对。顺序应该是先由 Egress 处理，再进隧道。

## 已确定的约束

| 项目 | 结论 |
|---|---|
| VPN 对端 | 所有虚拟机连同一个 VPN 服务器，服务器由我们自己运维 |
| VPN 协议 | WireGuard |
| 内网 IP | 每台虚拟机有独立的内网 IP，必须保留 |
| 规模 | 虚拟机数量增长很快 |
| Egress | 自己部署，多台虚拟机共享。实现应为 Envoy，**待确认** |

## 方案

把 VPN 客户端从虚拟机里拿出来，放到 Egress 之后的独立一层（VPN 网关）。VPN 接入方式从"每台虚拟机一条隧道"改为"一条站点到站点隧道加一块路由过来的地址"。

```
VM(真实IP) → Egress [识别来源 → 授权 → 注入凭证]
           → VPN 网关 [以该虚拟机的内网IP为源地址发起连接]
           ══ WireGuard 隧道 ══ VPN 服务器 [把地址块交给该网关] → 内网
```

虚拟机数量增长只是在映射表里多一条记录，不再多一条隧道。虚拟机里不再有 VPN 密钥。

### 组成部分

1. **地址分配表（控制面）**：虚拟机创建时分配内网 IP，销毁时回收。记录虚拟机真实 IP、内网 IP、允许访问的内网目的地。
2. **VPN 服务器**：给网关配一个 peer，`AllowedIPs` 是一整块地址。
3. **VPN 网关**：一条 WireGuard 隧道、一个四层的 Envoy、一张 nftables 映射表。
4. **Egress**：在原有处理之外，把去往内网的流量交给网关，并用 PROXY protocol 声明这条连接属于哪台虚拟机、要去哪里。

### 一条连接的完整路径

以虚拟机 `10.1.2.3`（内网 IP `100.64.0.7`）访问内网服务 `10.200.5.6:443` 为例。

去程：

1. 虚拟机向 `10.200.5.6:443` 发起连接，源地址是真实 IP `10.1.2.3`。
2. 流量被导到 Egress。Egress 还原目的地址，按来源识别虚拟机，检查授权，注入凭证。
3. Egress 连接 VPN 网关的 15001 端口，在连接开头发送 PROXY 头：源 `10.1.2.3`，目的 `10.200.5.6:443`。
4. 网关的 Envoy 读取 PROXY 头，以 `10.1.2.3` 为源地址、带标记 123，向 `10.200.5.6:443` 发起连接。
5. 网关的 nftables 把源地址换成 `100.64.0.7`，包进入隧道。
6. VPN 服务器确认源地址在该 peer 的 `AllowedIPs` 内，转发到内网。内网看到的来源是 `100.64.0.7`。

回程：

7. 内网服务回包到 `100.64.0.7`，经内网路由到 VPN 服务器，再按 `AllowedIPs` 发给网关。
8. 网关内核把目的地址还原成 `10.1.2.3`，并按连接标记把包交给本机的 Envoy。
9. Envoy 沿原连接把数据回给 Egress，Egress 回给虚拟机。

## 本地模拟测试

两个测试都不需要 root，全部在临时的网络命名空间里进行，不影响本机网络。

### 整条链路（需要 Envoy）

```bash
ENVOY=/path/to/envoy bash test/envoy-chain.sh
```

`ENVOY` 指向 Envoy 可执行文件，可从 [Envoy 的发布页](https://github.com/envoyproxy/envoy/releases)下载。测试搭出虚拟机、Egress、VPN 网关、内网服务四个节点，网关和 Egress 上各运行一个真实的 Envoy：

- 网关原样加载 `config/vpn-gateway/envoy.yaml` 和 `vpngw.nft`，路由按 `wg0.conf` 的内容配置。
- Egress 使用 `config/egress/vpn-gateway-cluster.yaml` 里的上游，只把网关域名换成测试地址。它的监听器是测试脚本里按"透明劫持"假设写的参考实现，分四层代理和七层代理两种接法。

检查的内容：

- 已登记的虚拟机访问内网服务，内网服务看到的来源是它的内网 IP。四层和七层两种接法都检查。
- 未登记的虚拟机被拦截。
- 登记后立即可以连通。
- 两台虚拟机交替发起 HTTP 请求时，内网服务看到的来源不串。

没有覆盖的内容：WireGuard 本身（用一对 veth 代替隧道）、真实的 Egress、TLS、主备切换和性能。

### 只测网关的内核路径（不需要 Envoy）

```bash
bash test/gateway-kernel-path.sh
```

用一个 Python 进程模拟网关 Envoy 的行为（绑定虚拟机地址并打标记），只验证 `vpngw.nft` 和策略路由。没有 Envoy 时可以用它快速检查映射规则的改动。

## 前提与待确认

这套配置假设 Egress 是**透明劫持**：虚拟机直接向内网服务的 IP 发起连接，Egress 用 `original_dst` 还原目的地址。这样 PROXY 头里的目的地址才是真正的内网服务，网关才知道该连谁。

如果 Egress 是显式代理，或者按域名选上游，PROXY 头里的目的地址就不是内网服务。那种情况下 Egress 到网关要改用 HTTP CONNECT 传递目的地，内网域名要在网关侧解析，`envoy.yaml` 和 `vpn-gateway-cluster.yaml` 都要重写。

需要向维护 Egress 的同事确认：

- [ ] Egress 确实基于 Envoy。
- [ ] Egress 的劫持方式是透明劫持，还是显式代理。
- [ ] Egress 当前如何识别来源虚拟机（应依赖虚拟化层保证的源 IP 或网卡）。

## 安全要点

- **凭证只对指定的服务注入，并且尽量用客户端证书。** 不按目的地限定时，虚拟机向任意站点发一个请求，对方就收到凭证；用令牌时，服务一旦回显请求头，令牌就回到虚拟机。控制点见 [docs/design.md](docs/design.md) 的“凭证不落到虚拟机”，实验结果见 [lab/eve-ng/README.md](lab/eve-ng/README.md)。
- **令牌和静态凭证要由服务端按来源地址限定。** 这两类凭证做不到虚拟机拿不到，只能做到泄露了在别处用不了。本方案保留了每台虚拟机独立的内网 IP，服务端能限定到单台虚拟机。服务接受凭证的每个入口都要被 Egress 覆盖。
- **不走 HTTP 的口令（数据库、缓存）Egress 注入不了，只能留在虚拟机里。** 要逐个登记为例外；服务能认客户端证书的，由 Egress 在四层代为出示。
- **两类凭证的做法后续要调整（2026-11-22 选定方向，未验证）。** 客户端证书改成 Egress 只用自己的一张证书，每个请求带一份短期的身份声明；不走 HTTP 的口令放到内网一侧、数据库前面的接入代理上。见 [docs/ha-scale-design.md](docs/ha-scale-design.md) 第 10 节。
- **Egress 到网关的上游连接要设空闲超时。** 七层处理时每个请求都会留下一条空闲连接，Envoy 默认 1 小时才回收。配置里设的是 10 秒，按业务调整。
- **Egress 要拒绝虚拟机访问网关所在的网段。** 否则虚拟机可以让 Egress 把自带伪造 PROXY 头的连接转给网关，冒充任意已登记的虚拟机。这一条是 EVE-NG 实验中发现并用对照测试证实的。
- **来源识别要防伪造。** 认错来源等于让一台虚拟机冒用另一台的内网 IP。要依赖虚拟化层保证的源 IP 或网卡，并开启防地址欺骗，不能用虚拟机自己携带的标识。
- **授权由 Egress 承担。** 以前 VPN 服务器逐台认证虚拟机，现在它信任的是网关。"哪台虚拟机能访问内网的什么"要在 Egress 上控制。内网侧按 IP 配置的访问控制仍然有效，因为内网 IP 没变。
- **虚拟机只能到达 Egress。** 网关的 15001 端口无条件信任 PROXY 头，只能对 Egress 实例开放。虚拟机如果能直接连到网关，就能冒充任意虚拟机。
- **吊销虚拟机里的旧 VPN 密钥。** 迁移完一台就删掉它在 VPN 服务器上的 peer，否则它仍可以绕过 Egress 直接拨号。
- **VPN 密钥只存在于网关。** 网关成为高价值目标，要按密钥托管设备的标准加固。

## 扩容与高可用

- **地址池一次留足。** 按几年后的规模规划，之后再扩很麻烦。
- **按单元扩展。** 一对主备网关加若干地址块算一个单元。容量不够时加一个单元和一个地址块，已有虚拟机不受影响。
- **主备切换。** 主备两台网关用同一对 WireGuard 密钥，同一时刻只启动一台。备机启动后发出第一个握手包，服务器会自动把对端地址更新为备机，服务器侧不用改配置。切换时已有连接会断，业务需要重连。映射表要同步到备机。
- **不使用 BGP 通告地址块。** WireGuard 按每个 peer 的 `AllowedIPs` 决定包发给谁，动态路由改不了它。地址块直接写在 `AllowedIPs` 里。

## 迁移步骤

`AllowedIPs` 是最长前缀匹配，所以新旧方式可以并存，逐台迁移：

1. 在 VPN 服务器上添加网关 peer，地址块覆盖现有虚拟机使用的内网地址段。此时所有虚拟机仍走各自的 `/32` peer，行为不变。
2. 部署 VPN 网关（WireGuard、Envoy、nftables），在 Egress 上加入指向网关的 cluster。
3. 选一台虚拟机：在映射表登记它的真实 IP 和现有内网 IP，停掉它的 VPN 客户端，把它去往内网的流量导向 Egress。
4. 在 VPN 服务器上删除这台虚拟机的 `/32` peer。它的地址落到网关 peer 上，旧密钥同时失效。
5. 验证后按批重复第 3、4 步。

## 验证清单

优先验证前三项，它们是整个方案能否成立的关键。八项都已在 EVE-NG 实验中通过，仍需在真实环境确认：

- [ ] 网关能按 PROXY 头里的目的地址连到内网服务。
- [ ] 内网服务看到的源地址是该虚拟机的内网 IP。
- [ ] 内网的回程包能回到网关的 Envoy，连接能正常收发数据。
- [ ] 映射表里未登记的虚拟机无法进入隧道。
- [ ] `/32` peer 与网关的地址块并存时，未迁移的虚拟机仍走原隧道。
- [ ] 删除一台虚拟机的 `/32` peer 后，它的流量改走网关，内网 IP 不变。
- [ ] 主备切换后新连接能建立。
- [ ] 到内网服务使用 TLS 时，网关上抓包只能看到密文。

## 已知限制

- **只覆盖 TCP。** Egress 到网关用的是代理方式。UDP 等流量要进内网，需要在网关上另做一对一的地址转换，Egress 对这部分只能做四层控制。
- **内网主动访问虚拟机没有覆盖。** 需要时可在网关上做一对一的目的地址转换，但这部分流量不经过 Egress 的七层处理，要单独决定放行哪些端口。
- **网关是有状态的。** 主备切换会中断已有连接。
