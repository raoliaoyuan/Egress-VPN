## 1. 结论

| 内容 | 方案里的位置 | 这一轮的结果 |
| --- | --- | --- |
| 网关的健康检查看隧道通不通 | 第 6 节 | 做了，成立。只断隧道、单方向丢包时热备 4.4 到 5.0 秒接管；只看进程的旧做法在同样的故障下不切换，故障期间 98.6% 的请求失败 |
| 转发进程异常、节点还在 | 第 12 节 | 成立。4.4 到 5.2 秒接管 |
| 主用网关在服务网段上被隔离 | 第 6 节没有写到 | **新发现的问题，已有对策。** 被隔离的网关听不到任何通告，会把所有单元的隧道都启动起来，连它平时不承载的单元也被拖下水（对照里那个单元 86.8% 的请求失败）。加上“够不着 Egress 的网关不参与选主”之后，不相干的单元 0 失败，它自己的单元 3.8 秒接管 |
| 主备之间互相听不到 | 第 6、12 节，列为没有解决 | 测出了后果，没有解决。两台都当主用，这个单元故障期间 20.7% 到 42.6% 的请求失败，时好时坏；身份没有串；互通恢复后 3.4 到 4.7 秒自己收敛 |
| 同网段内冒用源地址 | 第 5 节，一直列为未验证 | 成立。端口上绑定 MAC、IP 和 ARP 之后冒用的包到不了 Egress；对照里去掉绑定，冒用者被内网服务当成了受害者 |
| 多台 Egress 之间做等价多路径 | 第 5 节，没有验证 | 成立，并且量出了它和分片的差别：一台 Egress 断电，新连接 1.0 秒恢复（分片 4.2 秒），但两个块各断约一半的长连接；这台重新加入时又各断约一半 |
| 规则按服务写、凭证按身份查 | 第 10 节 | 成立。Envoy 的配置里没有凭证、没有虚拟机地址，条数和虚拟机数量无关；换表不重启、不断连接；每个请求多一次本机查询，延迟多约 0.6 毫秒 |
| 一张证书加身份声明 | 第 10 节，2026-11-22 选定 | 成立。十万个身份里实际访问过的 93976 个全部通过；拿别人的声明去重放的六种做法都被拒绝；网关改了地址时按声明认人的服务拒绝，只按来源地址认人的服务认错了人 |
| 多台 VPN 服务器同时工作，BGP 加 BFD | 第 7 节 | 成立。一台服务器断电，新连接 1.1 秒恢复，**已有的长连接一条不断**；单条隧道不通只影响 1.1 秒；BFD 在 WireGuard 接口上能正常工作 |
| 网关改成各自的密钥，接管改成通告地址块 | 第 6 节的“目标做法” | 成立。网关断电 3.9 秒，正常切回从 1.6 秒降到 0.7 秒 |
| 服务器和内网之间的有状态防火墙 | 第 7 节 | 共用一套时成立；各自独立时（对照）48% 的请求失败；“一主一备”的退路可行，但主用断电后已有连接是卡死而不是断开 |
| 和迁移并存 | 第 7 节，要重新验证 | 成立 |
| 默认经企业的互联网出口 | 第 8 节 | 成立。企业出口看到的来源是每台虚拟机的内网 IP；两种例外仍然本地直出；这条路不通时不放行，也不会改成本地直出 |
| 非 TCP 默认拒绝；基础设施的地址不能作为目的地址；审计 | 第 8、11 节 | 成立，见[第 8 节](#8-互联网出口和逐台阻断) |
| 逐台阻断 | 第 9 节 | 成立。三处一起执行 1.7 秒，被阻断的虚拟机已有的连接 0.2 秒后全部断开，别的虚拟机不受影响；三处各自单独也拦得住它该拦的 |

**身份有没有串：这一轮所有压测和故障注入里，身份不符的请求数仍然都是 0。**

没有做的见第 11 节，主要是控制面（节点自己拉取配置）、Envoy 的文件动态配置、域名策略和出口地址池、数据库的接入代理。

## 2. 环境的变化

**实验主机。** 从 12 核、32 GB 加到 24 核、48 GB（2026-11-22，用户同意）。同样的压测下，主机自身的 CPU 从第一轮的 70% 到 82% 降到 37% 到 46%，节点之间不再明显互相抢。

**节点。** 从十三个加到十七个，新增的四个是方案第 13 节列的：

| 节点 | 角色 | 这一轮用到了吗 |
| --- | --- | --- |
| `vpn-server-2` | 第二台 VPN 服务器 | 用到 |
| `rtr-core` | 内网核心路由器 | 用到 |
| `ctrl` | 控制面 | 节点已加，还没有用 |
| `corp-exit` | 模拟企业的互联网出口 | 用到 |

**拓扑的一处改动：内网服务挪到了内网核心路由器后面。** 原来 VPN 服务器直接接在内网服务的网段上。现在多了一个网段 CORE-NET（`10.200.0.0/24`）：两台 VPN 服务器和 `corp-exit` 接在上面，`rtr-core` 一头接它，一头接内网服务的网段（它接手了原来 VPN 服务器在那边的地址 `10.200.5.1`，内网服务的默认网关不用改）。只有一台服务器的形态下，两个方向都用静态路由，行为和原来一样。

**形态多了一种。**

| 形态 | 网关层 | VPN 服务器 | 哪个脚本建立 |
| --- | --- | --- | --- |
| 基础形态 | 一个单元，一主一备 | 一台 | `30-deploy-solution.sh` |
| 数据面 A 的规模化形态 | 两个单元加共享热备，每个单元一对密钥、一条隧道，只有主用启动 | 一台 | `80-scale-a.sh` |
| 多台 VPN 服务器 | 单元和热备不变；每台网关自己一对密钥，到每台服务器各一条隧道，一直建着 | 两台，BGP 加 BFD | `87-multi-server.sh` |

第 3 到 6 节在第二种形态上做，第 7、8 节在第三种上做。

**加核之后重跑了第一轮的验证**（`81-scale-a-verify.sh`），31 项全部通过，数字和第一轮接近：一台网关断电 4.2 秒，正常切回 1.6 秒，一台 Egress 断电 4.2 秒。

**全部做完之后，原有的阶段从头回归了一遍。** 拓扑改了（内网服务挪到内网核心后面），几个公共的文件也改了，所以从“现状”开始把每个阶段在十七个节点上重跑：

| 阶段 | 结果 |
| --- | --- |
| 服务（`10`） | 8 项全部通过 |
| 现状（`20`、`21`） | 10 项全部通过 |
| 部署新方案（`30`）、迁移一台（`40`） | 6 项全部通过 |
| 逐项验证（`50`） | 29 项全部通过 |
| 主备切换（`60`） | 21 项全部通过；断电 3.8 秒，正常切换 1.4 秒 |
| 凭证不落到虚拟机（`70`） | 40 项全部通过，另有 3 项对照成立 |
| 按凭证类型（`71`） | 34 项全部通过，另有 5 项对照成立 |
| 规模化形态（`80`、`81`） | 18 项、31 项全部通过 |
| 断电以外的故障，抽三项（`82`） | 21 项全部通过，另有 4 项对照成立 |

## 3. 断电以外的故障

脚本是 [`82-fault-a.sh`](../lab/eve-ng/phases/82-fault-a.sh)。故障都注入在 `gw-2`（单元 2 的主用，承载块 3）上，同时观察块 2（单元 1，不应受影响）和块 3。观察的方法和第一轮相同：每个块每秒 300 条新连接，各 60 条持续传输的长连接。

### 健康检查改了什么

第一轮的网关只检查 Envoy 进程在不在。现在是三项，脚本在 [`gateway-tunnel-check.sh`](../lab/eve-ng/files/gateway-tunnel-check.sh)：

| 检查 | 什么时候查 | 怎么查 | 连续几次失败后让出 |
| --- | --- | --- | --- |
| 转发进程 | 一直 | 进程在不在 | 2 次，每 2 秒一次 |
| 够不够得着 Egress | 一直 | 向每台 Egress 发一个探测包，有一台应答就算通 | 2 次，每秒一次 |
| 隧道通不通 | 本机承载着这个单元时 | 经隧道向 VPN 服务器后面的地址发一个探测包，一来一回都成功才算通 | 3 次，每秒一次 |

第三项的探测包要有一个源地址：每个单元在自己的地址块里留一个地址不分配给虚拟机（实验里单元 1 是 `100.64.3.253`，单元 2 是 `100.67.255.253`），只在隧道启动时配在隧道接口上。

另外，网关当上主用之后、启动隧道之前，会再确认一次够得着 Egress，够不着就不启动。原因见下面的“被隔离的网关”。

### 结果

| 故障 | 做法 | 块 3（故障所在的单元） | 块 2 |
| --- | --- | --- | --- |
| 转发进程停掉 | 现在的检查 | 新连接中断 4.4 秒，由 `gw-3` 接管，长连接全断 | 0 失败，长连接 0 中断 |
| 只断隧道，两个方向 | 对照：只看进程 | 不切换。故障的 20 秒里 98.6% 的请求失败；长连接没有断，卡了 26.6 秒 | 0 失败 |
| 只断隧道，两个方向 | 现在的检查 | 中断 5.0 秒，由 `gw-3` 接管 | 0 失败 |
| 单方向丢包：只丢服务器发给网关的 | 现在的检查 | 中断 4.4 秒，由 `gw-3` 接管 | 0 失败 |
| 主用在服务网段上被隔离 | 对照：不查够不够得着 Egress | 先由 `gw-3` 接管，十几秒后又断：`gw-2` 和 `gw-3` 同时启动着这个单元的隧道 | **86.8% 的请求失败**，见下文 |
| 主用在服务网段上被隔离 | 现在的检查 | 中断 3.8 秒；`gw-2` 自己停掉了隧道 | 0 失败 |
| 主备之间互相听不到 | 现在的检查 | 两台都是主用。故障的 30 秒里 20.7%（另一遍 42.6%）的请求失败 | 0 失败 |

所有情况下身份不符都是 0。接管类的故障在脚本里有数字标准（中断不超过 8 秒），都通过了。转发进程停掉、只断隧道、单方向丢包各跑过两遍，另一遍分别是 5.2、4.3、4.8 秒。

接管之后原来的主用恢复成备用，不抢回（网关单元配的是不抢占）；要切回去用“让出”开关。

### 被隔离的网关会把所有单元都抢过去

这是对照里发现的，设计文档没有写到。

`gw-2` 在服务网段（它和 Egress、和别的网关相连的那个网段）上收发都不通，到 VPN 服务器的那一侧正常。这时：

1. `gw-2` 听不到任何 VRRP 通告。它平时只是单元 1 的第三顺位，现在以为单元 1 的主用也没了，于是把单元 1 也接过来，启动单元 1 的隧道。
2. 同一个单元的网关共用一对密钥。`gw-2` 用单元 1 的密钥向 VPN 服务器握手，服务器把单元 1 的对端地址改成了 `gw-2`，并且和它建立了新的会话。
3. 正常工作的 `gw-1` 那一头的会话就此作废。它发出去的包服务器解不开，回程的包被送到 `gw-2`。`gw-1` 自己不知道，要等十几秒收不到任何应答才重新握手。

结果是一台只承载块 3 的网关出问题，块 2 也断了：对照里块 2 在故障期间 86.8% 的请求失败。隔离解除之后要多久恢复不固定，三遍分别是 2.6、2.8 和 23.6 秒，取决于 `gw-1` 什么时候重新握手。

对策是两处一起用：

- **够不着 Egress 的网关不参与选主。** 这项检查不管本机有没有承载单元都要做。它要比“听不到通告就接管”更快发现：实验里是 2 秒对 3.6 秒。
- **启动隧道之前再查一次。** 即使检查没赶上、网关先当上了主用，也不会启动隧道。

只用第一处、并且只在“本机承载着单元时”才查（这是先写出来的一版）不够：被隔离的网关会反复地当上主用、启动隧道、被检查打下去，每隔几秒抢一次对端。

用了对策之后：块 2 是 0 失败、长连接 0 中断，块 3 中断 3.8 秒。

这个问题的根子是“同一个单元的网关共用一对密钥”，也就是设计里的过渡做法。目标做法（每台网关自己的密钥，见第 7 节）没有这个问题。

### 主备之间互相听不到

`gw-2` 和 `gw-3` 之间的包互相丢掉，两台和 Egress、和 `gw-1` 都还通。这是设计文档列为“没有解决”的情况，这里只测后果，脚本里不设通过的标准。

- 两台都持有单元 2 的服务地址，都启动着单元 2 的隧道。
- 块 3 的请求时好时坏：故障的 30 秒里两遍分别有 20.7% 和 42.6% 失败，成片出现，每片几秒。
- 身份不符是 0。连接是连不通，不是串到别人身上。
- 互通恢复之后，优先级低的那台自己退回备用、停掉隧道；之后还会再断一阵（VPN 服务器上的会话要重建），3.4 到 4.7 秒后不再有失败。
- 块 2 不受影响。

要彻底防住仍然需要外部的归属仲裁。这次的数据可以用来判断它的优先级：后果是这个单元在分区期间约两到四成的请求失败，不扩散到别的单元，不出现身份错乱。

## 4. 同网段内冒用源地址

脚本是 [`83-spoof-samenet.sh`](../lab/eve-ng/phases/83-spoof-samenet.sh)。凭证和内网 IP 都按源地址选，所以同网段里一台虚拟机冒用另一台的地址，就同时拿到对方的两个身份。跨网段的冒用第一轮验证过（接入路由器的反向路径检查），同网段内的这一轮补上。

做法是在 `vm-farm` 上搭一个最小的“宿主机”：一个网桥当虚拟交换机，两个网络命名空间当两台虚拟机（下面叫甲、乙，地址在块 2 里、都登记过），各经一对虚拟网卡接到网桥的一个端口上。端口校验是一张 bridge 族的 nftables 表，每个端口只放行它自己的 MAC 和 IP，ARP 里声称的 IP 也必须是它自己的。

| 情况 | 结果 |
| --- | --- |
| 甲、乙各自正常访问内网 | 来源是各自的内网 IP |
| 开着端口校验，乙把甲的地址配到自己的网卡上，不断向网关声称“这个 IP 是我的” | 访问失败 |
| 同上，连网卡的 MAC 也改成甲的 | 访问失败 |
| 同上，数一数冒用的包有几个到了 Egress | 0 个 |
| 对照：关掉端口校验 | **冒用成功，内网服务看到的来源是甲的内网 IP**；到达 Egress 的包 11 个 |
| 恢复端口校验 | 冒用再次失败；甲自己照常 |

对照说明这个风险是真的：没有端口校验时，同网段里的一台虚拟机只要抢到 ARP，就能以另一台的身份访问内网，注入给它的也会是对方的凭证。

验证的范围：只验证了“在虚拟机接入的端口上绑定 MAC、IP、ARP”这个做法拦得住。生产里这一层是云平台或宿主机虚拟交换机的功能，它们怎么做、默认开没开，没有验证。

## 5. 多台 Egress 之间做等价多路径

脚本是 [`84-egress-ecmp.sh`](../lab/eve-ng/phases/84-egress-ecmp.sh)，跑完自己恢复成按块分片。

做法：

- 接入路由器上，三个块的默认路由改成两个下一跳（两台 Egress 的网卡地址），按五元组分流。
- 每台 Egress 有一个“就绪地址”：Envoy 的监听端口都在、劫持规则已加载，才把它配到网卡上（[`egress-ready.sh`](../lab/eve-ng/files/egress-ready.sh)）。接入路由器上的探测脚本每 0.2 秒探测一次这个地址，连续 3 次没有应答就把这台从路由里摘掉。
- Egress 的配置不用改：两台本来就相同，任何一台都能处理任何一台虚拟机。网关那一层也不用改。

| | 按块分片（第一轮和这一轮的基线） | 等价多路径 |
| --- | --- | --- |
| 平时 | 每个块只用一台 Egress | 每个块的流量两台都在处理，CPU 各 56% 到 58% |
| 身份 | 0 不符 | 0 不符。两个块共 95469 个请求 |
| 一台 Egress 断电，新连接 | 它负责的块中断 4.2 秒，另一个块 0 失败 | 两个块各中断 1.0 秒，各失败不到 100 个请求 |
| 一台 Egress 断电，长连接 | 它负责的块 60 条全断，另一个块 0 条 | 两个块各断约一半：60 条里 33 条和 30 条 |
| 这台 Egress 回来 | 抢回它的块，新连接 0 失败；这个块的长连接再断一次（按机制推的，没有专门测） | 新连接失败 0 到 1 个；两个块的长连接又各断约一半：都是 60 条里 29 条 |
| 同一台虚拟机访问公网（本地直出），对端看到的来源 | 固定 | 在两台 Egress 的出口地址之间变化 |

三点：

- **故障的影响从“一个块全断”变成“每个块断一部分”。** 新连接恢复快得多，因为不用等地址漂移，只要探测脚本摘掉下一跳。
- **增减实例会打扰无关的连接，这是实测到的。** 重新加入一台时，原来好好的连接有约一半被重新分到新加入的那台上，那台上没有它们的状态，于是中断。实验里只有两台，所以是一半；N 台变 N+1 台时大约是 N+1 分之一。能记住已有连接归属的负载均衡可以避免，实验里用的是普通的多路径路由，做不到。
- **“三台虚拟机连发 8 个请求，来源和凭证每次都是它自己的”也验证了**：请求落在哪台 Egress 上不影响注入的结果。

没有验证的：云平台上的网关型负载均衡。实验里的“接入路由器加探测脚本”只说明这个接入方式在数据面 A 下成立，不代表平台产品的行为。

### 按身份查

Envoy 的配置里每个服务端口一条规则，带两个过滤器：先删掉虚拟机自带的同名请求头，再去问本机的凭证代理。凭证代理应答里的请求头由 Envoy 写进请求。

| 检查 | 结果 |
| --- | --- |
| 三台虚拟机访问明文 HTTP 加令牌的服务 | 来源是各自的内网 IP，认出的身份是各自的 |
| 由 Egress 发起 TLS 加令牌的服务；共用账号的服务 | 同上；认出的是共用账号 |
| 访问公网上的指定服务 | 带的是它在那个服务上的那一份凭证 |
| 虚拟机自带一个假的凭证头 | 被覆盖成它自己的 |
| 表里没有凭证的来源访问同一个服务 | 不带凭证；它自带的凭证头被删掉，服务没有看到任何凭证 |
| 目的地址是公网、Host 写成内网服务的名字 | 不转发（404） |
| 两台 Egress 的 Envoy 配置文件里 | 凭证 0 个，虚拟机地址 0 个 |

### 更新和故障

| 检查 | 结果 |
| --- | --- |
| 换表（三台虚拟机加十万个模拟的身份，共 300021 条） | 下发到两台 Egress 并生效 1.5 到 2.1 秒 |
| 从表里去掉一台虚拟机；再加回来 | 它的请求立刻不带凭证；加回后又带上 |

| 两台 Egress 的 Envoy | 没有重启（进程号和启动时刻不变） |
| 凭证代理停掉 | 指定服务的请求返回 403，不会不带凭证转发出去；没有规则的端口、访问公网的其他站点不受影响 |
| 凭证代理重新启动 | 从本地的表恢复 |

这里的“下发”还是操作机经 SSH 把表放到节点上，然后用重命名替换。节点自己拉取、校验、回报版本的控制面没有做，见第 11 节。

### 身份声明

Egress 向校验代理发起 TLS 时出示的是它自己的一张证书（每台 Egress 一张，由同一个 CA 签发，带同一个名字）。凭证代理给每个“来源地址、服务”签一份 120 秒有效的声明（JWT，ES256，每台 Egress 一把签名密钥），里面写着虚拟机标识、它的内网 IP、发给哪个服务。校验代理验三样：客户端证书是 Egress 的；声明的签名、签发者、受众、有效期；声明里的内网 IP 等于连接的来源地址。通过之后把认出的调用方用请求头交给服务，声明本身不往后传。

| 检查 | 结果 |
| --- | --- |
| 三台虚拟机 | 服务认出的调用方、它的内网 IP、连接的来源三样都对 |
| 块 2、块 3 的模拟身份（分别由两台 Egress 签，经两个网关单元） | 都对 |
| 虚拟机自带“我是另一台”的请求头，再带一份假声明 | 服务认出的仍是它自己 |
| 服务把收到的请求头原样返回 | 里面没有声明：校验代理验完就拿掉了，所以令牌那种“被服务回显带回虚拟机”的路在这里不存在 |
| 同一台虚拟机对同一个服务，有效期内连取两次 | 是同一份，不是每个请求签一次 |
| 虚拟机自己对这个端口发起 TLS | 连不上 |

### 重放和伪造

假设攻击者已经拿到了一台虚拟机的声明（实验里是从凭证代理上直接取的，等于最坏情况），从内网里的另一台主机去访问校验代理：

| 手里有什么 | 结果 |
| --- | --- |
| 只有声明，没有证书 | 握手被拒绝 |
| 声明，加那台虚拟机原来的客户端证书（同一个 CA 签的，但不是 Egress 的） | 握手被拒绝 |
| 声明，加 Egress 的证书，但来源地址不是那台虚拟机的内网 IP | 403 |
| 对照：去掉“声明里的地址等于来源地址”这一条 | **同样的请求被当成那台虚拟机放行** |
| 有 Egress 的证书，不带声明 | 401 |
| 对照：一份各项都对、地址写的就是这台主机的声明 | 放行。说明下面四项被拒绝是因为各自那一处不对 |
| 过期的声明 | 401 |
| 受众是另一个服务的声明 | 403 |
| 签发者不对的声明 | 401 |
| 用另一把密钥签的声明 | 401 |

第四行的对照说明第三样校验不能省：没有它，拿到 Egress 的证书和任意一份声明就能从别处冒充那台虚拟机。倒数第五行的对照同时说明了这个做法的边界：Egress 的证书和签名密钥一起丢了，攻击者就能从它够得着的地址上声明任意身份。这和现在“Egress 上存着所有虚拟机的凭证”是同一个量级的风险，区别是事后只要换一把密钥。

### 网关改了地址

设计文档说，改用声明之后网关不再在身份的信任链里。实验里的做法是在承载单元 1 的网关上把一台虚拟机（乙）的映射改成另一台（甲）的内网 IP，模拟网关被攻破：

| 服务怎么认人 | 结果 |
| --- | --- |
| 对照：只按来源地址 | **把乙当成了甲的地址** |
| 按声明 | 拒绝（403）：声明里是乙的地址，来源是甲的地址 |
| 令牌，并且限定了来源 | 不认：乙的令牌从甲的地址发来 |

### 规模和开销

| | 结果 |
| --- | --- |
| 模拟的身份逐个经声明访问 | 块 2 访问到 47539 个，块 3 访问到 46437 个，被拒绝或失败的是 0 个。每个块登记了 50000 个，跑的时间不够长，没有全部轮到 |

这些数字里有实现的成分：凭证代理是 Python 写的单进程。它们说明“多一次本机查询”这个机制本身的代价不大，不是生产实现的容量。

### 实现上的发现

这几条是在 Envoy 1.40.2 上实际试出来的，设计文档里列为“要实测”：

- **外部授权过滤器可以按来源查、可以覆盖请求头。** 用它的 HTTP 方式。发给凭证代理的请求里，来源地址用 `%DOWNSTREAM_REMOTE_ADDRESS_WITHOUT_PORT%` 取自连接本身，会覆盖虚拟机自带的同名头。凭证代理应答里的请求头按名单写进原请求，同名的被覆盖。
- **查不到时虚拟机自带的头不会自动被删。** 要在外部授权过滤器前面放一个改写请求头的过滤器，先把同名的头删掉。
- **“声明里的地址等于连接的来源地址”写得出来，但有两个坎。** 一是授权策略的条件不能直接写成字符串，要写成解析好的语法树。二是 Envoy 关掉了条件表达式里的字符串拼接，而连接的来源地址是“地址:端口”的形式，没法直接比；只比开头又不严（`100.64.0.7` 是 `100.64.0.70` 的开头）。实验里的做法是先用改写请求头的过滤器把不带端口的来源地址写进一个请求头，再做相等比较。写法见校验代理的配置文件。
- **声明的签发者和受众要显式配置**，和官方文档说的一致。受众按“服务名:端口”配置之后，一个端口的声明拿到另一个端口确实用不了。

## 7. 多台 VPN 服务器同时工作

脚本是 [`87-multi-server.sh`](../lab/eve-ng/phases/87-multi-server.sh)（部署）和 [`88-multi-server-verify.sh`](../lab/eve-ng/phases/88-multi-server-verify.sh)（验证）。配置在 [`config/vpn-gateway/multi-server/`](../config/vpn-gateway/multi-server/)、[`config/vpn-server/multi-server/`](../config/vpn-server/multi-server/) 和 [`config/intranet-core/`](../config/intranet-core/)。

### 搭的是什么

这就是设计文档第 6 节的“目标做法”加第 7 节：

- **每台网关自己一对密钥，到每台 VPN 服务器各一条隧道。** 三台网关、两台服务器，一共六条，一直建着。服务器上每台网关一个隧道接口，各用一个端口。
- **每条隧道里一个 BGP 会话加 BFD。** 网关通告它此刻承载的单元的地址块，服务器通告内网网段。服务器和内网核心路由器之间同样是 BGP 加 BFD。路由软件是 FRR 8.4.4；BFD 是 300 毫秒一次、连续 3 次失败判定不通。
- **每个方向都是两条等价路由**，按五元组分摊：网关去内网经两台服务器，内网核心去每个地址块也经两台服务器。同一条连接的去程和回程可能经过不同的服务器。
- **谁承载哪个单元仍然由 keepalived 决定**（服务地址漂移），和原来一样。变的是接管的动作：不再启动隧道、等握手，而是开始通告这个单元的块。做法是加一条这个块的黑洞路由，FRR 看到本机路由表里有它才通告。
- **VPN 服务器上原来的那个接口保留**，只留给旧方式（虚拟机自带隧道）的对端。
- Egress 不用改。

部署后的检查 20 项全部通过：六条隧道、八个 BGP 会话（六个在隧道里，两个在服务器和内网核心之间）和对应的 BFD 会话都正常；内网核心上每个块有两个下一跳；三台虚拟机和模拟的身份来源都不变，凭证照常注入。

设计文档列为“要实测”的一条在这里有了结果：**BFD 在 WireGuard 接口上能正常工作**。

### 结果

| 检查 | 结果 |
| --- | --- |
| 两个块的每个身份都发请求 | 十万个身份全部访问到，失败 0，身份不符 0 |
| 两台服务器是不是都在转发 | 是。压测期间两台经隧道收发的字节数是 6893 万和 6858 万，各占一半 |
| **一台 VPN 服务器断电**（两台各断过一次） | 两个块的新连接各中断 1.1 秒；**60 条长连接一条没断**，最长卡了 1.5 秒，没有丢数据；网关没有切换 |
| 这台服务器回来、重新加入 | 新连接 0 失败，长连接 0 中断。会话建立、路由学到之后才有流量过来 |
| **一台网关断电**（单元 2 的主用） | 块 3 的新连接中断 3.9 秒，长连接全断；块 2 不受影响。热备接管后两台服务器上块 3 的路由都改指向它 |

| 和迁移并存 | 把一台虚拟机退回旧方式：它经自己的隧道访问内网，来源是它的内网 IP；同一个块里已迁移的虚拟机不受影响；再迁移回来，来源不变、凭证恢复注入 |

所有情况下身份不符都是 0。服务器断电和单条隧道不通在脚本里的标准是“长连接一条不断、新连接的中断不超过 3 秒”，网关断电是“不超过 8 秒”，都通过了。

和过渡做法（每个单元一对密钥，只有主用启动隧道）比：

| | 过渡做法 | 目标做法 |
| --- | --- | --- |
| 一台网关断电 | 4.2 秒 | 3.9 秒 |
| 正常切回 | 1.6 秒 | 0.7 秒 |
| 一台 VPN 服务器断电 | 没有第二台，全断 | 1.1 秒，长连接不断 |
| 被隔离的网关抢走别的单元的隧道 | 会，要靠健康检查防住（第 3 节） | 不会：密钥不共用 |

网关断电的时间差别不大，因为大头是检测（VRRP 通告间隔 1 秒，约 3.6 秒后判定）。正常切回不用等握手，所以明显快了。

### 和迁移并存是怎么做到的

设计文档说并存的依据要从“同一个接口里最长前缀优先”换成“路由表里最长前缀优先”，要重新验证。实验里的做法：

- 服务器上原来的那个接口，地址从整块改成只写它自己的一个地址。否则整个块的路由会落在这个接口上，盖住从网关学来的路由。
- 还没迁移的虚拟机各有一条 `/32` 的路由指向这个接口，由服务器通告给内网核心。它比网关通告的地址块更具体，所以回程只到这台服务器，不在两台之间分摊。
- 迁移一台，就删掉它的对端和这条 `/32`，通告随之撤销。

验证到的：内网核心上那台虚拟机的 `/32` 只指向它连着的那台服务器；迁移回来之后两处的 `/32` 都消失。

限制：旧方式的虚拟机只连着一台服务器，那台服务器断电它就断了，这和迁移之前一样。

### 服务器和内网之间的有状态防火墙

已确认真实环境里 VPN 服务器和内网之间有一层按连接状态过滤的防火墙，设计文档说它是“所有服务器共用一套”还是“每台服务器后面各自一套”决定了多台同时工作能不能成立。实验里两种都搭了。防火墙的规则是同一套：已建立的连接放行，新连接只允许从虚拟机一侧发起，其余丢弃；并且按严格的方式跟踪连接，不接受半路出现的连接（Linux 默认是宽松的，要专门关掉）。

| 放法 | 结果 |
| --- | --- |
| 共用一套，放在内网核心上 | 去程和回程在两台服务器之间任意分摊，44224 个请求失败 0；一台服务器断电，新连接 1.1 秒恢复，长连接 0 中断 |
| 对照：各自独立，每台服务器上一套 | **48% 的请求失败。** 回程从另一台服务器回来时，那台的防火墙没见过这条连接，当成无效包丢掉。两台各丢了一万一千多个包 |
| 退路：防火墙仍然各自独立，但让一台服务器做主用、另一台做备用 | 去程和回程都走主用那台，45771 个请求失败 0 |
| 退路下主用的服务器断电 | 新连接 1.1 秒后经备用的那台恢复。已有的 120 条长连接**没有收到断开，但此后发出的数据都没有回来**：备用那台的防火墙不认得它们，包被悄悄丢掉。连接是卡死，不是断开，要靠应用自己的超时发现 |

“一主一备”的做法是让备用的那台把自己通告的路径加长（两个方向都加），内网核心和网关上就只剩经主用的那一条。设计文档写的退路是“按块指定主用的服务器”，让两台各管各的块、都在干活。这里做的是它的简化形式：所有块都以同一台为主用。按块分开的做法在回程方向只是对不同的块加长不同服务器的路径，原理相同；去程方向要让网关按来源所在的块选服务器，这一步没有做。

### 主备之间互相听不到（目标做法下）

和第 3 节同一种故障，在这个形态下再测一遍。设计文档的预期是“两台都通告同一个块，回程在两台之间分摊，落到没有这条连接的那台上的包被拒绝，不会出现身份错乱”，实测相符：

- 两台都持有服务地址，都在通告块 3。
- 故障的 30 秒里块 3 有 45.3% 的请求失败（另一遍 44.6%），很均匀，每一秒都是一半左右。过渡做法下是时好时坏的 20% 到 43%。
- 身份不符是 0；块 2 不受影响。
- 互通恢复后 3.0 秒起不再失败。

这里又发现一个问题。第一遍测的时候，互通恢复之后块 3 **超过四十秒没有恢复**。原因在 Egress 一侧：分区期间后当上主用的那台最后发过“这个地址在我这里”的通告，Egress 的 ARP 缓存指着它；互通恢复后它退回备用、不再持有这个地址，而留下来的那台没有状态变化，不会主动重发通告。Egress 就一直把连接发给一台已经不持有这个地址的网关，直到 ARP 缓存过期。对策是让主用定期重发通告（实验里每 5 秒一次），加上之后是上面的 3.0 秒。这个问题和用哪种做法无关，过渡做法下也可能遇到，只是那几遍碰巧没有。

## 8. 互联网出口和逐台阻断

脚本是 [`89-corp-exit.sh`](../lab/eve-ng/phases/89-corp-exit.sh)，在多台 VPN 服务器的形态上做，跑完恢复原样。

### 经企业的互联网出口

做法和设计文档第 8 节写的一致：

- **Egress**：出口模式是生成配置时的一个选项。打开之后，去公网的连接不再交给“直接连原目的地”的上游，而是和去内网的连接一样交给 VPN 网关，PROXY 头里写着虚拟机的地址和公网的目的地址。例外有两种，命中的仍然本地直出：按目的地（实验里是公网站点的另一个地址，代表软件源）、按虚拟机（实验里是 `vm-c`）。
- **网关**：不用改配置。它照常把源地址换成内网 IP，按路由从隧道发出去。
- **路由**：内网核心路由器的默认路由指向企业出口，并用 BGP 通告给 VPN 服务器，服务器再通告给网关；网关一侧的隧道放行全部目的地址。服务器一侧不变：从隧道进来的包，源地址仍然只能是登记过的地址块。
- **企业出口**（`corp-exit`）：对虚拟机的内网 IP 做地址转换后发往公网，每条新连接记一行日志。上面放了一条管控策略（禁止访问公网站点的某个端口），代表企业已有的管控设备。

| 检查 | 结果 |
| --- | --- |
| 三个来源（块 1 的真实虚拟机、块 2 和块 3 的模拟身份）访问公网站点 | 对端看到的来源都是企业出口的地址 |
| 企业出口看到的来源 | 分别是这三个来源各自的内网 IP |
| 例外（按目的地）、例外（按虚拟机） | 对端看到的来源是 Egress 自己的出口地址 |
| 走例外的那台虚拟机访问内网 | 不受例外影响，仍然经网关，凭证照常注入 |
| 企业出口上的管控策略 | 对经它出去的虚拟机起作用；走例外的那台不经过它，访问同一个端口成功 |
| **企业出口不转发时** | 访问公网站点不成功；这期间从 Egress 的出口地址直接到达公网站点的包是 0 个；访问内网不受影响 |
| 企业出口恢复 | 又通了 |

网关上的默认路由是从 BGP 学来的两条等价路由（两条隧道），所以第 7 节验证的“一台服务器断电不断连接”对这条路同样适用，但没有专门在互联网流量上重测。

实验里的两处权宜：

- **多了一个“公网”网段。** 实验原来把承载网当公网用，公网站点和网关直接相连。经企业出口时这不对：网关会把公网站点当成直连，不走隧道。所以另用一个网关不直连的网段当公网。
- **网关上从 BGP 学来的路由放在主路由表里。** 设计文档说的是“带标记的流量的默认路由指向隧道”，也就是只有 Envoy 替虚拟机发起的连接才走这条默认路由。实验里网关没有别的默认路由，所以没有分开；生产里要分开，否则网关自己的流量也会进隧道。上面那个“公网站点和网关直连”的问题，在真实环境里如果网关和某些公网地址在同一个网段上也会遇到，分开之后才不会。

没有验证的：公网上要注入凭证的服务经企业出口（实验里那个服务的地址在承载网上）；域名策略；出口地址池；网关和隧道按全部互联网流量规划时的容量。

### 非 TCP 默认拒绝，基础设施的地址不能作为目的地址

改的是 Egress 节点上的内核规则（[`egress-strict.nft`](../lab/eve-ng/files/egress-strict.nft)）。原来的规则把虚拟机发来的非 TCP 流量都转发出去，并且只拦了网关所在的一个网段。

| 检查 | 改之前（对照） | 改之后 |
| --- | --- | --- |
| 虚拟机发往公网站点的 UDP | 到达 3 个 | 0 个 |
| 发往 443 端口的 UDP（QUIC 用的） | | 0 个 |
| ping 公网站点 | | 不通 |
| 发往指定解析器的 DNS | | 到达 |
| 发往别的地址的 DNS | | 0 个 |
| 已迁移的虚拟机向 VPN 服务器的隧道端口发 UDP | | 0 个 |
| 虚拟机让 Egress 去连接入网段上另一台 Egress 的 SSH 端口 | 到达 5 个包 | 0 个 |
| 虚拟机经隧道去连 VPN 服务器在内网一侧的地址 | 见下 | 0 个 |
| 虚拟机去连网关在承载网上的地址 | | 0 个 |
| 访问内网和公网 | | 照常 |

第二类是这次才注意到的：**虚拟机给的目的地址如果是基础设施的地址，Egress 会替它去连。** 对照里，虚拟机向接入网段上另一台 Egress 的 SSH 端口发起连接，Egress 照样接下来并从自己的网卡连了过去。实验主机的管理网也是这样够得着的。收紧之后的规则是：私有地址里只有登记过的内网服务网段可以作为目的地址，承载网上的基础设施地址另外列出来拦掉。

表里“经隧道去连 VPN 服务器在内网一侧的地址”这一行的对照没有成立：我原以为互联网流量改走隧道之后这个地址会变得可达，但收紧之前实测到达的包也是 0 个，原因没有查。所以这一行的“0 个”不能说明规则起了作用，只能说明这条路在实验里本来就不通。规则里仍然把内网核心网段拦掉了。

没有验证的：“还没迁移的虚拟机到 VPN 服务器的隧道报文放行”这一条规则写了，但没有在收紧的规则下拿一台旧方式的虚拟机实际测过；实时音视频（会议）的 UDP 怎么处理仍然没有定。

### 审计

Egress 的每条连接、每个请求记一行 JSON（Envoy 的访问日志）：时间、哪台虚拟机、去哪里、域名、走的哪个上游、用的哪个出口地址、结果。不记请求头；路径不带查询串。

| 检查 | 结果 |
| --- | --- |
| 访问内网服务的请求 | 有记录：虚拟机、目的地址、上游是哪个网关单元、状态码 |
| 经企业出口访问公网的连接 | 有记录 |
| 本地直出的连接 | 有记录，并且记下了用的出口地址 |
| 被拒绝的请求（Host 对不上，404） | 有记录 |
| 日志里出现的凭证 | 0 个 |
| 被拒绝的非 TCP | 在内核日志里有记录（限速） |

没有验证的：日志的汇集、保存和查询；量大时的开销。

### 逐台阻断

三处的动作和设计文档第 9 节一致：

| 位置 | 动作 |
| --- | --- |
| Egress（两台） | 把这台虚拟机的真实 IP 放进一个集合，在劫持之前丢掉它发来的一切；杀掉 Envoy 上和它之间已有的连接 |
| 网关（三台） | 删掉它的映射；清掉连接跟踪记录；杀掉以它的地址发起的上游连接 |
| VPN 服务器（两台） | 把它的内网 IP 放进拒绝名单，两个方向都丢弃 |

| 检查 | 结果 |
| --- | --- |
| 三处一起执行要多久 | 1.7 秒（操作机经 SSH 逐台执行，七个节点） |
| 被阻断的虚拟机：访问内网、经企业出口访问公网、本地直出的例外 | 三样都不通 |
| 它已有的 20 条长连接 | 全部断开，都在阻断发出后 0.2 秒 |
| 别的虚拟机 | 来源、凭证、公网访问都照常；另一个块的 40 条长连接一条没断 |
| 恢复 | 三样都通，内网 IP 不变 |
| 只在 VPN 服务器上拒绝 | 内网不通，经企业出口的公网不通；本地直出的例外不经过它，仍然通 |
| 只在网关上删掉映射 | 同上 |
| 只在 Egress 上拒绝 | 三样都不通 |

两点：

- **三处各自都拦得住它该拦的。** 设计文档说 VPN 服务器上的拒绝名单“不依赖 Egress 和网关”，实测如此：只在这一处操作，内网和经企业出口的公网就都断了。它拦不住的只有本地直出的例外，那条路不经过它。
- **已有连接是断开，不是卡死。** 靠的是在 Egress 上直接杀掉连接，被阻断的虚拟机会收到重置。

这里的“执行”仍然是操作机经 SSH 逐台做，1.7 秒是这种做法的时间。设计文档要的是改一下地址分配表里的状态、由通知下发，这依赖控制面，没有做。把拒绝名单做成 VPN 管理控制台上的一个操作也没有做。

## 9. 实验主机的内核崩溃

第一轮记过两次实验主机卡死，都在“数据面 B 只留一台网关、压大流量”这一项里，当时没有拿到报错。这一轮又出现了四次，特征完全相同：一个核在延时循环里空转，其余的核关中断停机。

| | 第三次 | 第四次 | 第五次 | 第六次 |
| --- | --- | --- | --- | --- |
| 发生时在跑什么 | 数据面 A，主备互相听不到的故障注入，每秒 600 条新连接 | 多台 VPN 服务器的形态，刚开始压测 | 数据面 A 的规模化形态，压测 | 多台 VPN 服务器的形态，一台服务器重新加入时 |
| 开机后多久 | 约 24 分钟 | 约 48 分钟 | 约 59 分钟 | 约 37 分钟 |
| 实验主机的核数 | 24 | 24 | 24 | 24 |

所以它**不是数据面 B 特有的，也不是核数不够造成的**。另外有一次是一个实验节点自己卡死（实验主机没事），重启那个节点就恢复了，原因没有查。

这一轮拿到了报错。第三次是从这台虚拟机的内存里只读地找出来的内核日志；之后把它的串口输出接到了宿主机上的一个日志文件，后两次直接有记录。第四次的报错：

```
BUG: #DF stack guard page was hit at … (stack is …)
stack guard page: 0000 [#1] PREEMPT SMP NOPTI
CPU: 3 PID: 0 Comm: swapper/3 Not tainted 6.7.5-eveng-6-ksm+ #1
RIP: 0010:local_clock_noinstr+0x9/0xd0
…
WARNING: stack recursion on stack type 5
Kernel panic - not syncing: Fatal exception in interrupt
```

第五次是 `BUG: unable to handle page fault for address: ffffffff82200be0`，同样在空闲的核上，最后是 `Kernel panic - not syncing: Attempted to kill the idle task!`。第六次和第四次是同一种（双重故障，栈溢出，空闲的核）。

能确定的：

- 有记录的几次出事的都是空闲的核（`swapper`）。
- 第三次和第五次，实验主机的核跳去执行的那个地址不在它自己内核的代码范围里。**这两个地址换算之后，都正好是实验节点（Debian 6.1）内核里缺页异常入口 `asm_exc_page_fault` 的地址**：节点内核里这个函数的链接地址是 `0xffffffff81c00be0`，两次出错的地址分别比它高 `0x1c000000` 和 `0x600000`，都是 2 MB 的整数倍，正是内核地址随机化的偏移该有的样子。
- 也就是说，实验主机的一个核在自己的上下文里，跑到了它里面某个节点的内核的异常处理入口上。那个地址在实验主机自己的页表里没有映射，于是出错，再出错，最后是致命错误。第四次的双重故障（异常处理用的栈溢出）是另一种表现。

推断（没有证实）：实验主机本身是一台虚拟机，实验节点是它里面的虚拟机。本该送进节点的一次缺页异常，被送到了实验主机这一层。这是嵌套虚拟化的缺陷，位置在宿主机的内核或者处理器这一层，和实验里跑什么内容没有固定关系。宿主机是 AMD 的处理器，内核 6.14；公开资料里能找到 2026 年一批针对 AMD 嵌套虚拟化的内核修复，但没有找到和这个现象对得上的报告，不能说就是其中哪一个。

试过的：

- 不向实验主机暴露两项嵌套虚拟化的加速（`vgif`、`v-vmsave-vmload`）：后面三次崩溃都发生在这之后，所以**没有用**。
- 怀疑过不可屏蔽中断太多：查了实验主机和节点上的计数，都是 0，排除。
- 怀疑过节点用了异步缺页通知：节点的内核日志里没有启用它的记录，实验主机上也没有换页，排除。

还有一个没有验证的猜测：实验主机从 12 核加到 24 核之后，空闲的核多了，而出事的都是空闲的核。12 核时这个问题两天里只在最重的压测里出现过两次，24 核时不到四个小时里出现了四次。样本太少，说明不了什么。

可以试的方向（都没有试）：换宿主机的内核版本；把实验主机的核数调回去；不用嵌套，把实验节点直接建在宿主机上。

对实验的影响：崩溃时正在跑的那一项作废，重置后重跑。重置之后十七个节点和各种形态都能自己恢复，不需要重新部署。

## 10. 方案要跟着改的地方

下面是这一轮的结果和 [ha-scale-design.md](ha-scale-design.md) 对不上、或者它没有写到的地方。

| 位置 | 文档里写的 | 这一轮的结果 |
| --- | --- | --- |
| 第 6 节，健康检查 | 要加上握手时间、BGP 状态、对服务器隧道内地址的探测，“还没有做” | 做了，用的是经隧道的探测，要一来一回都成功。握手时间不适合用来判断：隧道被阻断后它要两三分钟才过期 |
| 第 6 节，谁是主用 | 只讨论了主备之间的网络断开 | 还有一种更常见的情况：一台网关在服务网段上被隔离。过渡做法下它会把所有单元的隧道都抢过去。要加“够不着 Egress 的网关不参与选主” |
| 第 6 节，过渡做法下两台都当主用的后果 | “中断约 20 秒” | 两遍是故障期间 20.7% 和 42.6% 的请求失败，成片出现；互通恢复后 3.4 到 4.7 秒收敛 |
| 第 5 节，等价多路径 | 没有验证 | 数字见本文第 5 节。“普通的哈希会把一部分已有连接分到别的实例上”得到证实，两台时是一半 |
| 第 5 节，源地址校验 | 同网段内冒用没有做 | 做了，见本文第 4 节 |
| 第 10 节，按身份查 | 用外部授权过滤器，“要验证” | 成立。要补一句：查不到时虚拟机自带的头要另外删 |
| 第 10 节，校验代理上“声明里的地址等于来源地址” | 可能要用条件表达式，官方没有例子，要实测 | 写得出来，两个坎和绕法见本文第 6 节 |
| 第 10 节，“带回去的声明几分钟后过期” | | 更强：校验代理验完就把声明拿掉，服务根本收不到，也就带不回虚拟机 |
| 第 6 节，目标做法下两台都当主用的后果 | 两台都通告同一个块，这个单元的连接大面积失败，不会身份错乱 | 相符：约 45% 的请求失败，身份不符 0 |
| 第 6 节，没有写到 | | 两台都当主用的情况结束之后，Egress 的 ARP 缓存可能还指着退下来的那台。要让主用定期重发地址通告 |
| 第 7 节，BFD 跑在 WireGuard 接口上能不能稳定工作 | 要实测 | 能。300 毫秒乘 3 的参数下，服务器断电和单条隧道不通都是 1.1 秒恢复 |
| 第 7 节，防火墙各自独立时的退路 | 按块指定主用的服务器，“它那些块的连接会断，重连后恢复” | 退路可行。要补一句：主用断电后，已有的连接在备用那台的防火墙上是被悄悄丢包，表现为卡死，不是立刻断开 |
| 第 7 节，和迁移并存 | 要重新验证 | 成立。要补上做法：服务器上原来那个接口的地址要从整块改成单个地址；没迁移的虚拟机的 `/32` 要由服务器通告出去 |
| 第 8 节，经企业出口 | 网关上带标记的流量的默认路由指向隧道 | 成立。实验里没有把这条默认路由和网关自己的路由分开，生产里要分开，见本文第 8 节 |
| 第 8、11 节，Egress 拒绝虚拟机访问基础设施网段 | 拦全部基础设施网段 | 要写得更一般：私有地址里只有登记过的内网服务网段可以作为目的地址。对照里虚拟机确实能让 Egress 替它连到接入网段上的另一台机器 |
| 第 9 节，逐台阻断 | 具体写法、多久生效、已有连接是不是确实断了，要确认 | 三处的写法见 `89-corp-exit.sh`。已有连接 0.2 秒断开，靠的是在 Egress 上直接杀掉连接；只删映射和连接跟踪记录的话连接是卡死 |
| 第 13 节，资源 | 十七个节点合计约 17 GB | 十三个节点时已经分配了约 16.5 GB，十七个节点约 20 GB |
| 第 13 节，“这个实验证明不了什么” | 实验主机的内核崩溃只在数据面 B 只留一台网关时出现 | 不是。数据面 A、中等负载下也出现了，见本文第 9 节 |

## 11. 仍然没有验证的

- 真实的 Egress。
- **控制面**：节点自己拉取配置、校验、回报版本；控制面停掉之后数据面的行为；下发一份错误的配置。这一轮的“下发”和“阻断”都还是操作机经 SSH 推送。凭证代理“先完整解析再整张换上、有错保留旧的”验证了，但那只是其中一环。`ctrl` 节点已经加上，没有用到。
- **Envoy 的文件动态配置**：新增一个服务的规则时不重启、对已有连接的影响。
- **互联网出口里本地直出的那几项**：按域名的策略（由 Egress 自己解析、不采用虚拟机给的目的地址）、出口地址池、每台虚拟机的并发连接上限。
- 经企业出口：公网上要注入凭证的服务；一台 VPN 服务器或网关故障时互联网流量的表现（机制和内网流量相同，没有单独测）；网关把这条默认路由和自己的路由分开。
- 收紧的规则下，还没迁移的虚拟机的隧道报文是否照常放行；会议的 UDP。
- **数据库的接入代理**：真的 PostgreSQL 加 PgBouncer、MySQL。
- 逐台阻断做成地址分配表里的一个状态、由通知下发；VPN 管理控制台上的操作入口。
- 身份声明：各节点时钟有偏差时有效期的判断；校验的一侧按“这台 Egress 有没有资格替这个地址块签”来限制；声明复用多久合适。
- 归属仲裁：主备互相听不到时怎么防止两台都当主用。这一轮在两种做法下都只测了后果。
- 防火墙各自独立时“按块指定主用的服务器”里，网关按来源所在的块选服务器的那一半。
- 同时在线的规模：十万台虚拟机同时有连接的情况仍然没有测。
- 云平台上的行为：端口上的源地址校验、网关型负载均衡、地址漂移是否可用，都没有在真实的平台上试过。
- 各项检测参数怎么选：这一轮用的都是实验里随手定的值，没有系统地比较过。
- 实验主机内核崩溃的原因。
