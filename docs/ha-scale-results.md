## 1. 结论

**数据面 B 在实验里成立，五个验证点里四个成立，一个部分成立。**

| 验证点 | 结论 | 一句话的证据 |
| --- | --- | --- |
| 1 连接池按源地址隔离 | 成立 | 三种压法共 51 万个七层请求，内网服务看到的来源错的是 0 个。同一个身份的 40 个请求只用了 2 条上游连接，A 是 40 条 |
| 2 五元组冲突，分区能否避开 | 冲突确实出现；分区能避开，**但分区的位置和设计文档写的相反** | 不分区时同样的压法失败 3924 个、5702 个请求（两次），分区后都是 0 个。设计文档写的“虚拟机一侧分区”会让所有连接都不通，要改成上游一侧分区，见 [5.3](#53-验证点-2连接跟踪的五元组冲突) |
| 3 回程能交回 Egress 本机的 Envoy | 成立 | 靠一条策略路由；去掉它就不通，放回去恢复。和透明劫持的规则互不干扰 |
| 4 网关断电时长连接不断 | 成立 | 三次断电，60 条持续传输的长连接每次都全部存活，没有丢数据，最长卡了 1.5 秒。同一台网关上走 A 的 60 条每次全断 |
| 5 性能更好 | 部分成立 | 新建连接速率高 60% 到 100%，长连接的请求速率高 15% 到 60%。**大流量的 TCP 吞吐没有明显更好**：B 三台网关合起来和 A 的一台差不多（上行多两到三成，下行持平），B 单台网关能转发的流量是 A 单台的七成左右；总吞吐被实验平台的上限挡住了，见 [6 节的吞吐专项](#吞吐专项补测) |

**B 还能不能用：能。** 没有哪一条让它不成立。但它比设计文档里写的多三样东西才跑得起来（每台网关一条自己的隧道、多条等价路由加探测、网关的就绪地址），分区的做法也要改，见第 5 节和第 8 节。

**怎么看这两种数据面（按用户 2026-11-21 确认的情况）。** 目标规模是几万台虚拟机，十万个身份的测试是留了余量的上限。业务能接受切换时已有连接断开后重连，所以 A“网关故障时这个单元的连接全断”是可以接受的代价，不是不能用的理由；B 的价值主要看容量和吞吐。而互联网访问以后也要走隧道，网关、隧道、VPN 服务器要承载的流量会比只走内网时大得多。按这个标准，这次的数据对 B 并不一边倒：请求多、连接短的负载 B 明显好；大流量的吞吐 B 在这个实验里没有体现出优势：单台网关能转发的流量 B 比 A 低，三台合起来和 A 的一台差不多，再往上被实验平台的上限挡住，测不出来，见第 6 节。

**数据面 A 的多单元和共享热备成立。** 一台网关或一台 Egress 断电，只影响它负责的块，另一个块的新连接 0 失败、长连接 0 中断。共享热备 `gw-3` 接管一个单元约 3.8 秒（检测间隔 1 秒时）；把检测间隔调到 0.2 秒是 1.9 秒。

**十万个身份做到了。** 映射表 100003 条，从空表加载 0.4 秒，整表原子替换 0.57 秒，占内核内存约 23 MB。每个身份都实际发过请求并核对过来源。

**身份有没有串：所有压测和故障注入里，身份不符的请求数都是 0。**

**现有的阶段脚本（现状、迁移、主备切换、凭证）在改造后全部通过**，项数和改造前一样。

## 2. 环境和测法

### 拓扑

在原来的九个节点上加了四个：`vm-farm`（模拟大量虚拟机）、`rtr-acc`（接入路由器）、`egress-2`、`gw-3`。原来的 `egress` 改名 `egress-1`，它面向虚拟机的网卡从 VM-NET 改接到 ACC-NET，虚拟机的默认网关换成 `rtr-acc`。节点表见 [lab/eve-ng/README.md](../lab/eve-ng/README.md)。

| 层 | 节点 | 规格 |
| --- | --- | --- |
| 虚拟机 | `vm-a`、`vm-b`、`vm-c`（块 1），`vm-farm`（块 2、块 3） | 1 核；`vm-farm` 3 核 |
| 接入 | `rtr-acc` | 2 核 |
| Egress | `egress-1`、`egress-2` | 2 核，2 GB |
| 网关 | `gw-1`、`gw-2`、`gw-3` | 2 核，2 GB |
| VPN 服务器 | `vpn-server` | 2 核 |
| 内网 | `intranet-svc` | 2 核 |

改造前每个节点都是 1 核。实验主机本身没有动（12 核、31 GB）。

地址块和设计文档第 4 节一致：块 1 是 `10.1.2.0/24` 对 `100.64.0.0/22`，块 2 是 `10.2.0.0/16` 对 `100.66.0.0/16`，块 3 是 `10.3.0.0/16` 对 `100.67.0.0/16`。块 2、块 3 各登记了 50000 个身份（地址偏移 1 到 50000），第 i 个身份的真实地址和内网地址是两边的基地址各加 i。

### 三种形态

| 形态 | 网关层 | 哪个脚本建立 |
| --- | --- | --- |
| 基础形态 | 一个单元，`gw-1` 主用、`gw-2` 备用，`gw-3` 闲置 | `30-deploy-solution.sh` |
| 数据面 A 的规模化形态 | 两个单元加共享热备：单元 1（块 1、块 2）`gw-1` → `gw-3` → `gw-2`，单元 2（块 3）`gw-2` → `gw-3` → `gw-1` | `80-scale-a.sh` |
| 块 3 走数据面 B | 块 1、块 2 仍走 A；块 3 的地址转换在 Egress 上，三台网关同时转发 | `85-dataplane-b.sh` |

A 和 B 的对比都用块 3：同样的身份、同样的节点、同样的测法，只换数据面。

### 工具

现成的压测工具做不到“每条连接换一个源地址”和“核对每个响应里的来源”，所以自己写了三个，源码都在 [lab/eve-ng/files/](../lab/eve-ng/files/)：

- `labsrv.c`：内网服务节点上的服务端。HTTP 端口（8090、8091）对每个请求返回它看到的来源地址和端口；7000 端口原样回显。实验原有的回显服务是 Python 写的，每秒一两千个请求就到顶，压测时会先成为瓶颈。
- `labload.c`：发流量的客户端。每条连接绑定不同的源地址；每个响应都核对“内网服务看到的来源是不是这个身份应有的内网 IP”；按 0.1 秒一格记录成功和失败数。
- `stream-client.py`：一组持续传输的长连接。每条连接每 20 毫秒发一行带序号的数据，对端原样发回。记录连接断没断、相邻两行回来的最大间隔、发出和收回的行数之差。

Egress 对 8090 端口做七层处理，对 8091 只做四层转发，所以下文的“七层”“四层”就是这两个端口。TCP 吞吐用 iperf3，走四层转发。

### 度量的定义

| 度量 | 怎么得到 |
| --- | --- |
| 新连接多久恢复 | 每秒 300 条新连接（每条换一个身份，单次超时 1 秒）。从故障前最后一个“全部成功”的 0.1 秒格，到恢复后第一个“全部成功”的格，之间的时间。粒度 0.1 秒 |
| 已有连接是否存活 | 60 条持续传输的长连接，看断了几条；没断的看最长卡了多久、发出和收回的行数差多少 |
| 身份有没有串 | 每个响应里的来源地址和这个身份应有的内网 IP 逐个比对，不一致的个数 |
| 请求速率、建连速率、延迟 | 256 条并发连接、三个线程，跑 20 秒 |
| CPU | 压测中间一段，各节点 `/proc/stat` 的差值，占这个节点全部核的百分比 |

“断电”是用实验平台停止节点，等同于拔电源。停止命令发出到节点真正消失约 1.5 秒，下面的中断时长是从时间线算的，不含这一段。

## 3. 基线，以及基线阶段发现的三个问题

改拓扑之前，先在原来的九个节点（每个 1 核）上测了现有链路：`vm-a` 一个身份，经 `egress`、`gw-1`、`vpn-server` 到内网服务。

| 项目 | 改造前（1 核） | 改造后同一条链路的块 3（2 核，数据面 A） |
| --- | --- | --- |
| TCP 吞吐，上行 / 下行 | 2250 / 2279 Mbit/s | 1983 / 2710 Mbit/s |
| 新建连接，七层 / 四层 | 1062 / 864 条每秒 | 1974 / 2023 条每秒 |
| 长连接复用，七层 / 四层 | 4656 / 4904 个请求每秒 | 10728 / 15886 个请求每秒 |
| 延迟 p50，七层 | 2.7 毫秒（每秒 200 个请求） | 5.0 毫秒（每秒 500 个请求） |
| 主备切换：断电 / 正常切换 | 3.9 秒 / 1.4 秒 | 见第 4 节 |
| 先到顶的节点 | 网关、VPN 服务器（吞吐）；Egress、网关（请求） | 网关（93% 到 95%） |

两列的发流量节点、并发数、路径都不完全相同（改造后多了接入路由器一跳、身份从 1 个变成 5 万个），只能看量级。吞吐基本没有随核数增加，原因是它卡在 WireGuard 加解密和实验平台的虚拟网卡上，见第 9 节。

这组数字是修掉下面三个问题之后测的。按原样测的第一遍，数字低得多，而且测到一半 Egress 就连不上了。

### 问题一：连接跟踪表的上限太小

Egress 和网关上，连接跟踪表的上限是系统按内存算的默认值，1 GB 内存的节点只有 8192 条。一条 TCP 连接正常关闭之后，它的记录还要留 120 秒。所以**默认值下每秒只能持续新建约 68 条连接**，再多表就满了，新连接的包被丢弃。实验里每秒 200 个请求跑了十几秒，Egress 的表就满了，连管理口的 SSH 都进不去，等了两分钟才恢复。

修正：[lab/eve-ng/files/tune.sh](../lab/eve-ng/files/tune.sh) 把上限提到每 2 KB 内存一条（2 GB 的节点约一百万条），关闭后记录的保留时间降到 30 秒，Egress 和网关开机时执行。同一个脚本里还放宽了本机发起连接可用的源端口范围：数据面 A 里，一台 Egress 到一个网关单元的所有连接只有源端口不同，默认的两万八千个端口在建连速率高时不够用。

这是设计文档第 4 节“连接跟踪表的条数要按并发连接数调”的实测版本。生产环境的 Egress 和网关都要检查这个值。

### 问题二：Envoy 默认的熔断阈值

Envoy 默认每个上游集群最多 1024 条连接。本方案里，七层处理的每个请求都会在 Egress 到网关之间留下一条空闲 10 秒的连接（基础方案里已经实测过），所以**每秒一百多个请求，网关上的连接数就超过 1024**，超出的新连接一建立就被网关关掉，Egress 一侧表现为 503。实验里每秒 200 个请求时，约四成的请求返回 503。

修正：在 [config/egress/vpn-gateway-cluster.yaml](../config/egress/vpn-gateway-cluster.yaml) 和 [config/vpn-gateway/envoy.yaml](../config/vpn-gateway/envoy.yaml) 里加了 `circuit_breakers`。**这是方案配置的改动，不只是实验。** 数值按容量规划定：网关上的连接数约等于“活跃连接数 + 请求速率 × 空闲超时”。

### 问题三：接入路由器上策略路由和反向路径检查互相打架

接入路由器按源地址所在的块选路由表（设计文档第 5 节的做法），同时在虚拟机一侧的网卡上开了反向路径检查。结果虚拟机连自己的默认网关都 ping 不通：发给路由器自己的包，反查时命中了块的规则，出口成了 Egress 那一侧，和包进来的网卡不一致，被当成伪造的丢掉，连 ARP 请求都不应答。

修正：加一条优先级更高的规则，目的地址在虚拟机一侧的走主表（[lab/eve-ng/files/rtr-acc-boot.sh](../lab/eve-ng/files/rtr-acc-boot.sh)）。设计文档第 5 节的示意规则里没有这一条。

## 4. 数据面 A 的规模化形态

脚本：[80-scale-a.sh](../lab/eve-ng/phases/80-scale-a.sh) 部署，18 项检查全部通过；[81-scale-a-verify.sh](../lab/eve-ng/phases/81-scale-a-verify.sh) 验证，31 项检查全部通过，另有 1 项对照成立。

### 做了什么

- **接入层。** `rtr-acc` 按块引流；两台 Egress 之间用 keepalived 漂移接入地址，每组块一个 VRRP 实例（`10.1.254.101` 是块 1、块 2，`10.1.254.102` 是块 3）。两台 Egress 的配置完全相同。
- **网关层。** 每个单元一对密钥、一条隧道、一个服务地址、Envoy 里一个监听器。三台网关都带两个单元的全部配置和全量映射表，每个单元一个 VRRP 实例，优先级决定顺位。这是设计文档里的“过渡做法”。
- **一台网关同时承载两个单元**时，两条隧道都通往同一个内网网段。做法是每个单元一张路由表，按连接的源地址（虚拟机真实 IP）选表；每条隧道只放行自己单元的地址块。配置在 [config/vpn-gateway/multi-unit/](../config/vpn-gateway/multi-unit/)。部署过程中 `gw-1` 实际同时承载过两个单元，两个块的身份都正确。
- **正常切换。** 每个单元一个“让出”开关（keepalived 的 `track_file`），只让出一个单元，不影响同一台网关上的另一个。
- **映射表的下发**改成整表原子替换（[lab/eve-ng/files/load-map.sh](../lab/eve-ng/files/load-map.sh)）：清空和重新填入写在一个文件里，作为一个事务提交。原来的做法是先清空再逐条添加，中间有一段表是空的。

### 身份

每个块的五万个身份都发了请求，七层、四层各一遍：

| | 请求数 | 失败 | 身份不符 | 覆盖的身份 |
| --- | --- | --- | --- | --- |
| 块 2，七层 / 四层 | 74698 / 74227 | 0 / 0 | 0 / 0 | 全部 50000 个 |
| 块 3，七层 / 四层 | 75218 / 72757 | 0 / 0 | 0 / 0 | 全部 50000 个 |

块里没有登记的地址访问内网被拦截。块 3 的身份访问公网，来源是 `egress-2` 的地址；块 2 的是 `egress-1` 的。

### 十万条映射

在没有承载任何单元的 `gw-3` 上测，表里 100003 条：

| 项目 | 结果 |
| --- | --- |
| 从空表加载 | 0.40 秒 |
| 表里已有全量时整表原子替换 | 0.57 秒（其中 nft 提交 0.46 秒，其余是生成文件） |
| 单条登记 / 单条注销 | 0.003 秒 / 0.023 秒 |
| 下发的文件大小 | 2.9 MB |
| 内核内存增加 | 约 23 MB |
| 在承载流量的网关上连续 6 次整表替换，期间每秒 500 个请求 | 失败 0，身份不符 0 |

Egress 上数据面 B 用的那张同样的表：从空表加载 0.52 秒，整表替换 0.74 秒，内存相同。

这回答了设计文档第 14 节的“十万条记录的映射表，整表原子替换要多久”：不到一秒，替换期间不影响流量。

### 一台网关断电

断电的是 `gw-2`（单元 2 的主用，承载块 3）。同时观察块 2（单元 1，`gw-1`）。

| | 块 3（受影响） | 块 2（不该受影响） |
| --- | --- | --- |
| 新连接中断 | 3.8 秒，失败 860 个请求 | 0 秒，失败 0 个 |
| 60 条长连接 | 全部中断 | 0 条中断，最长卡 0.07 秒 |
| 身份不符 | 0 | 0 |

共享热备 `gw-3` 接管了单元 2 的服务地址和隧道，没有启动单元 1 的隧道。VPN 服务器的配置没有改动，它看到单元 2 的对端地址自动变成 `gw-3` 的。`gw-2` 重新开机后是备用，自动加载了全量映射表，不抢回。之后用“让出”开关把单元 2 从 `gw-3` 正常切回 `gw-2`：中断 1.8 秒，失败 192 个请求。

3.8 秒里大部分是检测时间：VRRP 通告间隔 1 秒，备用在连续约 3 个间隔收不到通告后才接管，和基础形态的 3.9 秒一致。**把通告间隔改成 0.2 秒重测：中断 1.9 秒，失败 233 个请求**，正常切回 1.5 秒。剩下的是隧道握手和 Egress 上连接重建的时间。已有的连接在两种间隔下都全部中断。

### 一台 Egress 断电

断电的是 `egress-2`（负责块 3）。

| | 块 3（受影响） | 块 2（不该受影响） |
| --- | --- | --- |
| 新连接中断 | 4.0 秒，失败 840 个请求 | 0 秒，失败 0 个 |
| 60 条长连接 | 全部中断 | 0 条中断 |
| 身份不符 | 0 | 0 |

`egress-1` 接管了块 3 的接入地址。接管后块 3 访问内网的来源不变（仍经单元 2）；访问公网的来源变成 `egress-1` 的地址，这是预期的，出口地址跟着 Egress 走。`egress-2` 重新开机后自己把块 3 拿了回去，期间每秒 300 条的新连接失败 0 到 1 个。拿回去时块 3 的已有连接会再断一次，这一点是推断，长连接没有专门测。

### 跨网段冒用源地址

`vm-farm` 冒用块 1 里 `vm-a` 的地址发包：接入路由器开着反向路径检查时，到达 Egress 的包是 0 个；关掉检查后到达了 6 个（对照成立）；恢复后又是 0 个。

这只拦住了跨网段的冒用。同网段内的冒用（设计文档里说用网络命名空间加网桥按端口过滤来测）没有做。

### 5.1 为了让它成立，引入了什么

设计文档第 6 节写了 Egress 上的内核规则和“网关按块选回程”。实际跑起来还缺四样东西，下面是我选的最小做法和理由。

**一、每台网关一条自己的隧道。** B 要求同一个块由多台网关同时承载。WireGuard 的一个接口上，同一段地址只能属于一个对端，回程只能交给一台网关。所以 VPN 服务器上给每台网关建一个接口（`wg-gw1` 到 `wg-gw3`，各用一个端口），每个接口上只有这一台网关一个对端；网关一侧是 `wgb`，用自己的密钥，一直建着。原来的 `wg0`（每台虚拟机的对端、网关单元的对端）不动，可以并存。这其实就是设计文档第 7 节“每条邻接一个隧道接口”的做法，只是这里只有一台服务器。用户已确认（2026-11-21）真实的 VPN 服务器是自己搭的 WireGuard，可以在上面配置隧道接口和路由，所以这一条在真实环境里有条件落地，不是只在实验里成立的权宜做法。

**二、多条等价路由。** VPN 服务器上，块 3 的回程是一条有三个下一跳的路由，每个下一跳是一台网关的隧道接口；Egress 上，去内网的路由同样有三个下一跳，指向三台网关。两处都按五元组分流（`fib_multipath_hash_policy=1`），所以同一条连接的去程和回程可能经过不同的网关。

**三、探测并摘除不通的下一跳。** 一台网关断电后，要把它从上面两条路由里摘掉。完整的做法是隧道里跑 BGP 加 BFD，那是第 2 期的内容，不在这次范围内（用户已确认真实环境里内网的路由设备可以和 VPN 服务器跑动态路由，所以这个方向可行，只是这次没有验证）。这次用一个小脚本代替（[nh-monitor.py](../lab/eve-ng/files/nh-monitor.py)）：每 0.2 秒 ping 一次每个下一跳，连续 3 次没有应答就重写路由把它摘掉，恢复后放回。Egress 和 VPN 服务器上各跑一个。**所以这次没有装路由软件。**

**四、网关的就绪地址。** 第一版里 Egress 探测的是网关的网卡地址。结果网关重新开机时，网卡一通就被放回路由，而那时它的隧道还没握手、转发还没打开，约 1 秒内分给它的新连接都失败了（60 个）。改成网关自己判断：转发已打开、并且经自己的隧道能 ping 通 VPN 服务器时，才在面向 Egress 的网卡上配一个“就绪地址”，Egress 只探测这个地址（[gateway-b-health.sh](../lab/eve-ng/files/gateway-b-health.sh)）。网关上隧道也改成在转发就绪之后才启动。改完之后网关重新加入期间 0 失败。

**回程怎么回到处理这条连接的 Egress。** 设计文档说“Egress 向网关通告它负责的块”。这次没有用路由协议，做法是每组块在 Egress 和网关之间的网段上再放一个“回程地址”，和接入地址放在同一个 VRRP 实例里一起漂移。网关上对块 3 的路由指向这个回程地址。这样“谁持有接入地址”和“回程回到谁”始终是同一台，Egress 断电的测试里两个地址确实一起切到了 `egress-1`。

**其余按设计文档做了的：** 网关上不跟踪这些连接、只放行两个方向、两个方向的 SYN 都压最大报文段长度；Envoy 多两个监听器，上游连接用虚拟机的真实 IP 作源地址并打标记；Egress 上的映射表、标记、地址转换、出口检查。

**没有做的：** 走数据面 B 的监听器不注入凭证。实验里走 B 的只有 `vm-farm` 模拟的块 3，凭证的验证都在走 A 的块 1 上。B 下面的凭证注入用的是同一个七层机制，但没有验证过。

### 5.2 验证点 1：连接池按源地址隔离

**成立。**

| 压法（都是七层） | 请求数 | 失败 | 身份不符 |
| --- | --- | --- | --- |
| 五万个身份轮流，每条下游连接发 20 个请求 | 256305 | 0 | 0 |
| 8 个身份挤在 128 条并发连接上，上游连接大量复用 | 161910 | 0 | 0 |
| 每个请求新建连接，每条换一个身份 | 93989 | 0 | 0 |

第二种压法是最容易串的情况：同一个身份有很多并发请求，Envoy 一定会复用上游连接；如果连接池不按源地址分开，别的身份的请求就会落到这些连接上。

**同一个身份的请求确实复用了上游连接。** 同一个身份连发 40 个请求，每个请求一条新的下游连接，看内网服务一共见到几个不同的来源端口：数据面 A 是 40 个（每个请求一条上游连接），数据面 B 是 2 个（Envoy 有两个工作线程，每个线程一个连接池）。

由此带来的差别，每秒 500 个请求跑完时各处留着的连接数：

| | 网关上 | 内网服务上（五万个身份轮流） | 内网服务上（只有 100 个身份） |
| --- | --- | --- | --- |
| 数据面 A | 约 7900 | 约 3700 | 约 3800 |
| 数据面 B | 0 | 约 3700 | 约 200 |

A 里网关和内网服务上常驻的空闲连接数是“请求速率 × 空闲超时”，和有多少台虚拟机无关。B 里网关上没有连接；内网服务上的空闲连接数不超过“活跃的虚拟机数 × Envoy 的工作线程数”。每个请求都来自不同虚拟机时两者一样多，请求集中在少数虚拟机上时 B 少得多。

### 5.3 验证点 2：连接跟踪的五元组冲突

**冲突确实出现。分区能避开，但分区的位置要和设计文档写的反过来。**

**先说位置。** 设计文档第 6 节的示意规则把虚拟机一侧的连接放进单独的分区。照这样加载之后，Egress 上所有连接都不通了，包括走数据面 A 的块和去公网的流量。原因：透明劫持靠 `SO_ORIGINAL_DST` 取回虚拟机原本要访问的地址，内核只在默认分区里找这条记录；虚拟机一侧换了分区，Envoy 取不到目的地址，连接一建立就被重置。

改成把**上游一侧**放进单独的分区、虚拟机一侧留在默认分区：本机发出的带标记的包，和从网关一侧回来、目的地址在走数据面 B 的内网地址块里的包。改完之后全部正常。规则在 [config/dataplane-b/egress-b.nft](../config/dataplane-b/egress-b.nft)。

**再说冲突本身。** 构造方法：一个身份同时开一万条连接，源端口固定为 20000 到 29999，占掉 Egress 可选源端口范围的约两成。Egress 的上游连接用同一个源地址、由内核另选端口，约两成会选到虚拟机正在用的端口。

| | 成功 | 失败 | 开成的连接 |
| --- | --- | --- | --- |
| 不分区（对照），第一次 | 55410 | 3924（超时 3364，连接被断 560） | 一万条里一直有开不成、反复重试的 |
| 不分区（对照），第二次 | 53212 | 5702（超时 4982，连接被断 720） | 同上 |
| 上游一侧分区，两次 | 59986、59954 | 0、0 | 一万条全部开成 |

两种情况下身份不符都是 0：冲突的后果是连不通，不是串到别人身上。

实际发生的概率比这个构造的低得多，要“同一台虚拟机到同一个目的地址和端口的并发连接”占到源端口范围的可观比例才会明显。但它是随连接数增长的，分区之后彻底没有。

### 5.4 验证点 3：回程能交回 Egress 本机的 Envoy

**成立。**

- 块 3 的请求经七层、四层都正常，来源是对应的内网 IP。
- 靠的是一条策略路由：从网关一侧进来、带标记的包查一张只有“交给本机”的路由表。**对照**：去掉这条规则，块 3 的请求不通（回程包按目的地址被转发回了虚拟机一侧）；放回去之后连发 20 个请求全部成功。
- 反向路径检查在 Egress 上是关着的（系统默认）。开着的话会不会拦回程包，没有测。
- 和透明劫持的规则互不干扰：同一台 Egress 上，块 3 去公网的流量照常（不带标记，不做地址映射）；另一台 Egress 也加载了数据面 B 的规则，它上面走数据面 A 的块 2、块 1 照常，`vm-a` 的令牌和客户端证书照常注入。

有一个没查清的现象，见第 9 节。

### 5.5 验证点 4：网关断电时长连接不断

**成立。**

断电的是 `gw-1`。它在数据面 A 里是单元 1 的主用，承载块 2；在数据面 B 里是承载块 3 的三台网关之一。**同一台网关、同一次断电，两种数据面的块同时受到影响**，结果直接可比。做了三次：

| | 块 3（数据面 B） | 块 2（数据面 A，对照） |
| --- | --- | --- |
| 60 条长连接 | **三次都是 0 条中断**，发出和收回的行数相等 | 三次都是 60 条全部中断 |
| 没断的长连接最长卡了多久 | 1.5、1.5、1.1 秒；卡过 0.3 秒以上的有 27、34、28 条 | 不适用 |
| 新连接中断 | 1.0、0.9、0.9 秒，失败 111、85、90 个请求 | 4.4、4.4、4.7 秒，失败 1012、998、1083 个 |
| 身份不符 | 0 | 0 |

- 约一半的长连接卡过，因为一条连接的去程和回程各有三分之一的可能经过断电的那台，两个方向至少一个中招的比例是九分之五。卡住的时间是探测发现（0.6 秒）加上 TCP 重传的等待。
- 断电后 Egress 和 VPN 服务器上的路由都剩两个下一跳。
- `gw-1` 重新开机后重新加入转发，期间块 3 每秒 300 条的新连接失败 0 个，长连接 0 条中断，最长卡 0.06 秒（这是加了就绪地址之后的结果，之前见 5.1）。

这也回答了设计文档第 14 节的一条：去程和回程走不同的网关时，沿途没有东西因为只看到一半的连接而丢包。前提是网关上对这些连接不做跟踪。

**这个结论不能直接推到真实环境。** 实验里从网关到内网服务这段路上没有任何按连接状态过滤的设备，VPN 服务器也只有一台。用户确认真实环境里 VPN 服务器和内网之间有一层有状态的防火墙（各台服务器共用一套还是各自独立还不知道）。只有一台 VPN 服务器时，一条连接的两个方向都经过它，网关之间怎么分流防火墙看不到，这种情况和实验一致；有多台 VPN 服务器、防火墙又是各自独立时，去程和回程可能经过不同的防火墙，只看到半条连接的那一台会丢包。这种情况实验里没有，也没有测。

### 5.6 Egress 断电（数据面 B）

断电的是 `egress-2`，做了两次。块 3 的新连接中断 4.1 秒、4.4 秒，失败 893、950 个请求，60 条长连接全部中断；块 2 不受影响。`egress-1` 同时接管了块 3 的接入地址和回程地址，接管后块 3 仍走数据面 B，来源不变。`egress-2` 恢复后自己拿回了块 3，期间失败 1 个请求。

和数据面 A 的 4.0 秒一样：Egress 这一层的故障行为和数据面无关。B 把连接状态从网关挪到了 Egress，Egress 断电时这些连接照样全断。

- **数据面 A：下行约 2.3 到 2.5 Gbit/s。** 这时网关的 CPU 是 91% 到 97%，到顶了。
- **数据面 B：下行约 1.7 到 1.9 Gbit/s。** 流从 1 条加到 8 条，吞吐没有再涨（反而略低），网关的 CPU 停在 80% 左右，其中约一半是软中断。也就是说它已经到顶，只是没有表现为 100%：实验节点的网卡只有一个队列，逐包转发的活大部分压在一个核上。
- **所以按“一台网关能转发多大的流量”算，B 的一台是 A 的一台的七成左右。** B 里网关是内核逐包转发，每个包都是隧道放得下的大小；A 里网关终结了 TCP，两边各自可以合并成大包处理。这个解释是推测，没有拆开验证。
- **上行时网关的上限两种数据面都没有测出来。** 上行 1.7 到 2.3 Gbit/s 时网关只用了三到六成，先卡住的是别处，见下一条。

**B 加网关有没有用，以及总吞吐卡在哪：**

- B 从一台网关加到三台，下行从约 1.7 涨到 2.5 到 2.6 Gbit/s（约加五成），上行从约 1.7 涨到 2.2 到 2.3（约加三成）。有叠加，但远不到三倍。
- 三台时每台网关只用了三到五成，卡住的不是网关。A 的一台网关下行也是 2.3 到 2.5 Gbit/s。**两种数据面的总吞吐都停在 2.3 到 2.6 Gbit/s 附近。**
- 不是 VPN 服务器的核数：从 2 核加到 4 核，A 的上行 8 流从 1716 涨到 1924（加 12%），B 从 2177 到 2287（加 5%），下行没有变化。它 2 核时平均 CPU 是 62% 到 87%，看上去像瓶颈，加核之后证明主要不是。
- 我的判断是卡在实验平台上：每个节点的虚拟网卡只有一个队列、没有内核加速，所有流量都要挤过几条公共的链路（接入路由器到 Egress、VPN 服务器到内网服务）；压到最大时实验主机自己的 CPU 也到了 70% 到 79%。这是推断，没有逐条链路去证实。
- 所以“B 的吞吐随网关台数叠加”这件事，这个实验只证明了“从一台到三台有增加”，叠加到什么程度被平台的上限挡住了，测不出来。

**放在一起看：** 这台实验主机上，A 用一台网关、B 用三台网关，总吞吐差不多（下行 2.4 对 2.5 到 2.6，上行 1.7 到 1.9 对 2.2 到 2.3 Gbit/s）。B 在上行多两成到三成，下行持平。要让 B 在大流量上体现出优势，得有多台网关同时吃满才行，而这里平台先到顶了。互联网流量也走隧道之后这一点最要紧，但它需要一个没有这种公共瓶颈的环境才能下结论（多台物理机，或者至少网卡有多队列和内核加速）。

### 故障

| 项目 | 数据面 A | 数据面 B |
| --- | --- | --- |
| 一台网关断电：新连接多久恢复 | 3.8 到 4.7 秒（检测间隔 1 秒）；1.9 秒（检测间隔 0.2 秒） | 0.9 到 1.0 秒（探测间隔 0.2 秒） |

## 9. 没有验证的，和已知的问题

**没有验证的：**

- 真实的 Egress。数据面 B 需要在 Egress 节点上加内核规则、路由和探测，Envoy 要有网络管理权限，这些真实的 Egress 接不接受还不知道。
- 数据面 B 下的凭证注入。
- 并发的规模。十万个身份是“映射表的条数”和“每个身份都发过请求”；同时在线的连接最多测到一万条（一个身份）和三万条左右的空闲连接。十万台虚拟机同时有连接的情况没有测。
- 只阻断隧道的 UDP、单方向丢包、主备之间网络断开（两台都以为自己是主用）。设计文档把最后一种列为“先测出实际后果”，这次没有测。
- VPN 服务器故障。只有一台。观察到一个相关的现象：服务器上的隧道接口重建之后，要等网关那一头下一次发包才会重新握手，网关配的保活是 25 秒，所以最长要等这么久。
- 真实的 VPN 服务器做不做地址转换，它和内网之间有没有有状态的防火墙，这两点还没有确认。实验里两者都没有。前一条影响两种数据面：做了地址转换，内网就看不到每台虚拟机各自的内网 IP。后一条主要影响数据面 B 加上多台 VPN 服务器的情况：去程和回程可能经过不同的服务器，有状态的防火墙只看到半条连接会丢包；只有一台服务器时两个方向都过它，实验里验证的“去程回程走不同网关不丢包”只到网关这一层。
- 同网段内冒用别人的源地址。
- 数据面 B 里网关“按来源限制源地址”是按网卡地址（MAC）认 Egress 的，没有测伪造。同一个二层网段里它是可以伪造的。
- 数据面 A 的健康检查仍然只看 Envoy 进程在不在。设计文档说要看隧道通不通，没有做。数据面 B 的就绪地址做了这件事。
- 探测脚本是为了让 B 在实验里成立写的最小实现，不是生产方案。

**已知的问题：**

- **实验主机卡死过两次，都在同一项测试里，原因不明。两次都是重置后恢复的。**
  - 第一次：2026-11-21 约 18:20，吞吐补测做到“数据面 B 只留一台网关”的第二遍。EVE 那台虚拟机不再响应：进程还在，只有一个核在空转，网卡收到 ARP 不应答，十三个节点全部连不上。
  - 重置之前在宿主机上只读取到的证据：十二个 vCPU 线程里只有 CPU 0 占 99.9%，其余都是 0；监视器里 CPU 0 在客户机的内核态（CPL=0，没有停机，中断是开的），指令指针 RIP=ffffffffaeabe027，隔 5 秒再取还是同一个值；宿主机当时有 85 GB 可用内存，日志里没有内存不足或 KVM 的报错。这说明是客户机（EVE）的内核卡在同一处不动，不是宿主机的问题。
  - 经用户同意，18:30 重置了这台虚拟机（没有改它的配置），用 `lab-up.sh`（不带 `--recreate`）拉起节点。EVE 上一次启动的内核日志停在卡死前约二十分钟的正常消息上，没有留下报错。**重启之后实验自己恢复了**：三个块都通，数据面 B 的三条路都在，接入地址各在其位；只有网关单元 2 落在了 `gw-1` 上（网关单元配的是不抢占，全部重启后谁当主用看谁先起来）。
  - 第二次：18:51，重新做“数据面 B 只留一台网关”这一项，第三遍中途又卡死，现象相同，这次空转的是 CPU 4。按用户的要求没有再重置。
  - 第二次在宿主机上只读取到的证据（18:55，一次列出全部十二个核）：CPU 0 到 3、5 到 11 都停在同一个地址（RIP=ffffffffa4a604c1），是关着中断停机的状态；只有 CPU 4 在跑，内核态、中断开着，指令指针在 ffffffffa5abe027 和 ffffffffa5abe040 之间来回。第一次卡死时 CPU 0 的指令指针是 ffffffffaeabe027，两次的低位 abe027 完全相同，只差内核地址随机化的偏移，也就是**两次停在同一个函数的同一条指令附近**。
  - 由此的推断（没有符号表，也没有看到报错的文字，不能算证实）：一个核开着中断在延时循环里空转、其余的核被关中断停机，是 Linux 内核出现致命错误（panic）之后的典型状态。也就是说 EVE 的内核两次都是在同一个地方出了致命错误，而不是慢慢卡住。出错时打印的内容没有留下：这台虚拟机的显示是串口，当时没有人接着看。第一次取证时只看了 CPU 0，其余核的状态没有取。
  - 两次之间，同样的压法在别的情况下（数据面 A、数据面 B 三台网关，VPN 服务器 2 核和 4 核）跑了四组、每组十二轮，都没有出事；更早的压测和故障注入跑过几十轮也没有。**只在“数据面 B 只留一台网关”时出现**，两次分别是开始后约五分钟和约四分钟。这只是相关，原因我没有查出来：卡死的是 EVE 自己的内核，它用的是嵌套虚拟化和很老的 QEMU（2.4）。这种情况下所有流量都由一台网关的内核逐包转发，是不是它触发的不知道。
  - 经用户再次同意，18:58 第二次重置。之后只做了恢复，没有再跑那一项：拉起节点，把实验里 VPN 服务器这个节点从 4 核改回 2 核，把网关单元 2 用“让出”开关挪回 `gw-2`，重新执行 `85-dataplane-b.sh`，16 项检查全部通过。
  - 影响：这一项的数字不完整（见第 6 节）。不要再跑 `B_ONLY=…` 这种情况，除非是专门去查这个问题。
- **实验平台的虚拟网卡是瓶颈之一。** 节点的网卡只有一个队列，没有用内核加速，多核节点上开了收包分摊（RPS）也只是缓解。吞吐在 1 核和 2 核时差不多（约 2 Gbit/s），就是这个原因加上 WireGuard。
- **压到最大时实验主机的 CPU 用到 70% 到 82%。** B 的最大值很可能被主机压低了，因为 B 同时用到的节点更多。所以表里 B 的优势可能偏保守，但没法在这台主机上证实。
- **验证点 3 的对照之后有一次没查清的失败。** 去掉策略路由再放回去之后的头一两秒里，同一个身份连发 6 个请求有 1 个被重置，之后正常。连发 200 个请求、以及几十万请求的压测里都没有再出现。脚本里现在是放回去之后等 8 秒再检查。我的猜测是对照期间内网服务重发的握手包在规则恢复后回来造成的，没有证实。
- **清空 Egress 的连接跟踪表会让内网服务上留下关不掉的连接。** 测试中间清过表（以及做“不分区”的对照时去掉过分区规则），当时上游有两万多条空闲连接，它们后来的关闭包认不出属于哪条连接、不做地址转换、被出口检查丢掉，内网服务那一头就一直留着。这是测试操作造成的，正常的关闭没有问题（抓包确认过）；验证脚本现在在这两种操作之前先等空闲连接关完，跑完之后内网服务上不再有残留。但它说明数据面 B 下 Egress 的连接跟踪表丢了（清空、重启），对端不会收到通知。数据面 A 的网关有同样的性质。
- **数据面 A 的多单元配置和基础配置不能直接互换。** 从多单元退回基础形态要先清掉几张路由表，见第 7 节。
