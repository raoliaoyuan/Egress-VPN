# 到企业内网的通路：三种方式的对比和产品形态建议

2026-11-21

本文回答一个问题：流量经过 Egress、做完地址转换之后，用什么方式送到企业内网。对比了三种方式，给出产品形态的建议，并说明现有实现离这个建议还差什么。方案背景见 [design.md](design.md)，高可用和规模化的设计见 [ha-scale-design.md](ha-scale-design.md)，实验数据见 [ha-scale-results.md](ha-scale-results.md)。

> **读之前先看这三条。**
>
> - 三种方式里只有方式 1 在实验里验证过。方式 2、方式 3 没有做过实验，关于它们的内容是按通用网络机制推出来的。
> - 实验里的 Egress 是参考实现，真实的 Egress 没有验证过。
> - 建议的产品形态里有几样东西现在还不存在，见[第 9 节](#9-现有实现数据面-a和建议的差距)。

## 1. 结论

**不在三种方式里选一种，而是把“到内网的通路”做成可以替换的。**

- 产品自带三样：Egress、地址转换服务、隧道的两端（本端的网关和企业边界上的接入端）。
- 隧道底下走公网、SD-WAN 还是专线，由客户决定。对隧道来说它们都只是一条能通 IP 的路。
- 默认用内置隧道。它对客户网络的要求最少，在任何云上都能部署，防冒用靠密钥而不靠网段封闭，也是唯一验证过的。
- 流量很大、客户又有私网互联时，可以不用隧道，地址转换服务把报文直接路由给客户的设备。
- 隧道协议不能只有 WireGuard，要加上 IPsec，否则进不了只认 IPsec 的企业。

现有的数据面 A 就是“默认模式”的雏形，方向一致，不需要推倒重来。差距在于地址转换和隧道在配置里绑死了，见第 9 节。

## 2. 已经定下来的前提

以下三条是 2026-11-21 确认的，本文在这个基础上讨论。

**Egress 保持独立。** Egress 只负责劫持流量、注入凭证，并把“这条连接来自哪台虚拟机、原本要去哪”告诉后面的服务。它不做地址转换，不建隧道，不要求改内核。这关系到产品定位：Egress 可以单独交付，后面接什么由部署决定。

因此 [ha-scale-design.md](ha-scale-design.md) 里的数据面 B（地址转换放到 Egress 上）不再是候选，那份文档还没有按这个决定更新。放弃 B 意味着放弃它在实验里表现出的三点：网关故障时已有连接不断、新建连接速率更高、多台网关同时工作。业务方已确认可以接受故障切换时重连，所以第一条不构成障碍。

**不在 Egress 上建隧道。** 理由有三条：

- 隧道密钥会和凭证落在同一层，而 Egress 是暴露面最大的一层。
- WireGuard 的服务器靠公钥认对端，每个对端都要事先登记。Egress 每次扩缩容都要同步改企业一侧的配置。
- Egress 的维护方要一起管 VPN。

**地址转换之后的那一层保留。** 讨论的范围因此收窄为：地址转换服务后面接什么通路。

## 3. 组件和职责

```
虚拟机 ──► Egress ──► 地址转换服务 ──► 通路 ──► 企业内网
           注入凭证     查映射表         隧道、SD-WAN
           传递来源     改来源地址       或专线
```

| 组件 | 做什么 | 知道什么 |
| --- | --- | --- |
| Egress | 终结虚拟机的连接，注入凭证，向后发起新连接，在连接开头用 PROXY protocol 写明虚拟机的真实地址和原本的目的地址 | 凭证。不知道内网 IP |
| 地址转换服务 | 读出真实地址，查映射表，把来源改成这台虚拟机专属的内网 IP，再发往内网 | 映射表（真实地址对内网 IP）。不知道凭证 |
| 通路 | 把改好来源的报文送到企业内网，把回程送回来 | 只看到内网 IP |

地址转换服务有连接状态，回程必须回到持有这条连接的那一台。所以同一个地址块同一时刻只能由一台承载，高可用靠“分单元加共享热备”，故障切换时这个单元的连接全断，扩容靠加单元。这一点三种方式都一样，不随通路变化。

内网 IP 的地址块和映射表由客户决定：地址块从客户自己的地址规划里分配，映射表登记每台虚拟机对应哪个内网 IP。

## 4. 要对比的三种方式

1. **WireGuard 网关。** 地址转换服务和 WireGuard 客户端在同一台机器上（叫 VPN 网关），经站点到站点的隧道连到企业边界上的 WireGuard 服务器，再进内网。实验里的数据面 A 就是这种。
2. **SD-WAN。** 独立的地址转换服务，后面对接 SD-WAN 的站点到站点连接。
3. **专线。** 独立的地址转换服务，后面对接专线。

## 5. 这三种方式不在同一层

把它们并列成三个选项并不准确：

- WireGuard 是一种隧道；SD-WAN 是一整套组网产品；专线是一条线路。
- 它们可以叠加：隧道可以跑在专线或 SD-WAN 上面，SD-WAN 自己也常以专线为底层。大公司常见的做法是组合，例如专线为主、VPN 为备。

对产品来说，真正的区别只有两种**交接方式**：

| 交接方式 | 含义 | 对应 |
| --- | --- | --- |
| 内置隧道 | 产品自己把报文封进隧道，隧道另一端在企业边界。底层网络只看到隧道两端的地址，看不到内网 IP | 方式 1。底下可以是公网、SD-WAN 或专线 |
| 三层直接交接 | 地址转换服务把改好来源的报文直接路由给客户的设备。底层网络要认识并放行这些内网 IP | 方式 2、方式 3 |

## 6. 逐项对比

| | 方式 1：WireGuard 网关 | 方式 2：SD-WAN | 方式 3：专线 |
| --- | --- | --- | --- |
| **安全** | | | |
| 隧道密钥 | 在网关上，由我们管 | 在 SD-WAN 设备上，由客户或厂商管 | 没有，除非另加加密 |
| 通路加密 | 有 | 通常有，看具体产品 | 默认没有 |
| 防止别的机器冒用内网 IP | 隧道把地址块绑定到网关的密钥，没有密钥发不进去 | 靠网段封闭，加上入口按来源过滤 | 同方式 2 |
| 对公网的暴露 | 企业边界要开一个隧道端口 | 看具体产品 | 没有 |
| **可用性** | | | |
| 通路自身的高可用 | 我们自己做。企业一侧的服务器多活还没做 | SD-WAN 自带多链路和切换 | 要两条不同路由的线，或留 VPN 作备份 |
| 地址转换服务故障切换 | 实测 1.9 到 3.8 秒，连接全断 | 少了隧道握手，应该更快，未测 | 同方式 2 |
| **性能** | | | |
| 吞吐 | 实测单台下行 2.3 到 2.5 Gbit/s，卡在加密 | 看设备规格和授权 | 没有加密开销，瓶颈移到地址转换服务 |
| **成本** | | | |
| 费用 | 软件加公网带宽，最低 | 设备和授权，授权常按带宽计 | 按带宽和距离长期计费，冗余要翻倍 |
| 开通周期 | 最短 | 客户已有则短，新建则长 | 客户已有则短，新建最长 |
| **可移植性** | | | |
| 对客户网络的要求 | 边界上能放一个隧道端点，并给地址块配回程路由 | 客户已有 SD-WAN 并允许接入 | 客户已有专线或愿意新拉 |
| 在公有云上 | 最容易：云网络只看到网关自己的地址 | 云网络要放行并路由这些内网 IP | 同方式 2，限制通常更多 |
| **迁移** | | | |
| 新旧并存 | 已验证：在同一台服务器上删掉虚拟机的对端即可 | 要靠明细路由区分两条路径，需重新设计 | 同方式 2 |

方式 1 一栏的数字来自 [ha-scale-results.md](ha-scale-results.md)，是每个节点 2 核的虚拟化实验环境里测到的，只能做相对比较，不是生产容量。

关于“防冒用”一行要补一句：隧道绑定的是“地址块对网关的密钥”，不是“单个内网 IP 对某台虚拟机”。单个 IP 的对应关系靠地址转换服务的映射表保证，企业一侧仍应按来源过滤。

## 7. 各自容易踩的坑

**方式 1**

- 很多大公司的边界设备只支持 IPsec，安全部门也可能不批准自建 WireGuard。这是它在可移植性上最大的短板，也是第 8 节建议加 IPsec 的原因。
- 企业一侧的隧道端点现在是单点。互联网流量也走这条路以后，它和网关都要扩，多活还没有做。
- 隧道封装会缩短可用的报文长度。数据面 A 里网关自己在隧道接口上发起连接，分段大小自动按隧道算，实验里没有遇到问题；隧道再叠到别的封装上时要重新确认。
- 地址转换和加密在同一台机器上抢 CPU。加密占满时会影响代理和健康检查。

**方式 2**

- SD-WAN 各家互不兼容，产品没法自带，只能对接客户已有的那一套。
- SD-WAN 设备可能自己再做一次地址转换，或按应用改变路径。前者会让内网看不到虚拟机专属的 IP，后者会让回程到不了持有连接的那台地址转换服务。必须逐家验证。
- 授权带宽会成为吞吐的硬上限。
- 客户或厂商不一定允许产品自动修改路由和策略。

**方式 3**

- 两条专线可能共用同一个机房、管道或云网关，名义上冗余，实际是一个故障点。
- 合规要求加密时要再加一层，加密的开销和密钥管理又回来了。
- 公有云的专线接入对“来源不是云内地址的报文”常有限制，取决于云厂商。
- 以后互联网流量也从企业出口出去，路径变长，跨地域时延迟会增加。

**三种方式都有的**

- 内网 IP 地址块可能和客户已有的地址冲突，必须由客户分配。
- 有状态防火墙要求同一条连接的去程和回程经过同一台。入口多于一个时要保证每个单元的路径对称。
- 迁移期间，同一个内网 IP 在任何时刻只能有一条生效的路径。

## 8. 建议的产品形态

### 产品提供什么，客户提供什么

| 产品提供 | 客户提供 |
| --- | --- |
| Egress：凭证注入，用 PROXY protocol 传递虚拟机的真实地址和目的地址 | 两端之间的 IP 连通：公网、SD-WAN、专线都可以 |
| 地址转换服务：映射表管理、地址转换、单元和热备 | 内网 IP 的地址块和分配规则 |
| 隧道的两端：本端的网关，企业边界上的接入端 | 企业内网把地址块的回程路由指向接入端 |
| 逐台阻断的接口、审计记录 | 防火墙策略，并保证去程和回程经过同一台有状态防火墙 |

### 两种交接模式

- **内置隧道（默认）。** 适用于所有情况。隧道可以跑在公网上，也可以跑在客户的 SD-WAN 或专线上。
- **三层直接交接。** 地址转换服务后面不建隧道，报文直接路由给客户的设备，用静态路由或动态路由。适用于流量很大、客户有私网互联的情况。

内置隧道还要留一个口子：企业一侧可以不用我们的接入端，而是用客户边界上已有的设备，这通常要求 IPsec。

### 怎么选

| 客户的情况 | 建议 |
| --- | --- |
| 没有现成的私网互联，或者要尽快上线 | 内置隧道，走公网 |
| 有 SD-WAN 或专线，流量不大 | 内置隧道，跑在它上面。配置和别的客户一致，防冒用仍然靠密钥 |
| 有专线，流量很大，例如互联网流量也走这条路 | 三层直接交接 |
| 边界只允许用自己的 IPsec 设备 | 本端网关用 IPsec 对接客户的设备 |
| 为了这件事专门新建 SD-WAN | 不建议。SD-WAN 的价值在于复用已有的 |

对本项目自己的环境：现在继续用方式 1。等互联网流量也走这条路、单台网关的吞吐不够时，再评估专线。

### 任何通路都要满足的条件

接入一种新的通路之前，按下面这张表逐项确认。

| 方面 | 要确认的 |
| --- | --- |
| 来源地址 | 企业内网的服务看到的来源，是不是虚拟机专属的内网 IP。途中任何一处再做地址转换都不行 |
| 回程 | 回程能不能回到持有这条连接的那台地址转换服务 |
| 防冒用 | 除了地址转换服务，还有没有别的入口能发出这些来源地址的报文 |
| 故障 | 通路和地址转换服务各自故障时，多久恢复，已有连接怎么样 |
| 容量 | 带宽、每秒报文数、并发连接数，以及故障后集中重连的峰值 |
| 报文长度 | 封装之后可用的长度，路径上是否放行相关的 ICMP |
| 迁移 | 旧路径和新路径并存时，每个内网 IP 的归属是否明确，能否回退 |

## 9. 现有实现（数据面 A）和建议的差距

**数据面 A 把地址转换和隧道放在同一台网关上，这符合建议里的默认模式。** 建议并不要求两者分成两台机器。差距在于两者在配置里绑在一起，隧道换不掉：

| 现在的做法 | 要改成 |
| --- | --- |
| 地址转换、出口检查、回程标记的规则都按 WireGuard 接口的名字写（见 [`config/vpn-gateway/multi-unit/vpngw.nft`](../config/vpn-gateway/multi-unit/vpngw.nft)） | 按“出口接口”写。出口可以是隧道，也可以是一块普通网卡 |
| 单元的接管动作就是“启动这个单元的隧道”，由 keepalived 的通知脚本触发 | 接管动作可以替换：启动隧道、通告路由，或者调用云平台的接口 |
| 隧道只有 WireGuard | 加上 IPsec |
| 没有不建隧道的模式 | 加上三层直接交接 |
| 企业一侧是手工配置的一台 WireGuard 服务器，单点 | 做成产品的接入端，支持多台 |
| 每个单元可用的地址块直接写在规则里 | 由客户的配置生成 |

### 要不要把地址转换和隧道拆成两台机器

| | 放在同一台（现在的做法） | 拆成两台 |
| --- | --- | --- |
| 机器和跳数 | 少一层，少一跳 | 多一层 |
| 高可用 | 一套主备管两件事 | 两层各自要做 |
| 防冒用 | 改好来源的报文不出机器就进了隧道 | 两台之间的网段要封闭 |
| 扩容 | 两者一起扩 | 可以分开扩 |
| 密钥和映射表 | 在同一台上 | 分开放 |
| CPU | 加密和代理互相抢 | 互不影响 |

建议：默认仍然放在同一台，作为一个可部署的单位，内部分成“地址转换”和“出口”两个模块；拆开作为部署选项。三层直接交接的模式下没有隧道，这个问题不存在。

## 10. 产品化之前要补的事

和选哪种通路无关，都要做。

1. **Egress 到地址转换服务之间要有认证。** PROXY protocol 本身不防伪造，地址转换服务无条件相信里面写的地址。实验里只按来源地址放行，做成产品要换成双向证书认证。
2. **服务地址的接管不能只靠 VRRP。** 多数公有云不支持，接管方式要能按环境替换。
3. **内网 IP 地址块由客户分配。** 实验里用的那几段在别的企业可能已被占用。
4. **阻断的语义要写清楚。** 只拦新连接，还是连已有连接一起断；地址回收之后多久能分给别的虚拟机。
5. **容量不能只看吞吐。** 还要测并发连接数、连接跟踪表、每个来源地址的可用端口数，以及故障后集中重连的峰值。
6. **支持哪些协议要写清楚。** 现在验证的是 TCP。UDP 和别的协议没有验证。

## 11. 没有验证的

- 方式 2、方式 3 整体没有做过实验。
- 内置隧道跑在 SD-WAN 或专线上，没有做过。
- IPsec 对接、三层直接交接、产品化的接入端，都还不存在。
- 公有云上的部署没有做过。第 6 节里关于公有云的判断取决于云厂商。
- 第 6 节里的费用和开通周期只是定性的比较，没有询过价。
- 真实的 Egress 能不能按要求发出 PROXY protocol，没有验证过。实验里用的是参考实现。

## 12. 这份对比是怎么做的

同一份问题说明交给两个模型各自独立分析，再核对分歧：一个是 Claude，另一个是 OpenAI 的 Codex。两边的主要结论一致：通路应该做成可替换的，三种方式不在同一层，Egress 到地址转换服务之间需要认证，VRRP 在云上不通用。

有三处不同，本文的处理如下：

- **默认用什么。** Codex 认为 WireGuard 只应作为参考实现，理由是大公司更愿意复用已有的网络；它标明这是推测。本文把内置隧道作为默认，理由是它是产品唯一能自己完整交付的通路。两者不矛盾：默认带隧道，同时支持直接对接客户的网络。
- **防冒用的强度。** Codex 指出隧道绑定的是地址块对网关，不是单个 IP 对虚拟机。本文采纳，见第 6 节表后的说明。
- **以虚拟机真实地址发起连接会不会被云平台拦掉。** Codex 有这个担心。本文不同意：在现有实现里，来源在报文离开机器之前就改成了内网 IP，真实地址不会出现在线路上，这在实验里验证过。会被云平台检查的是内网 IP，已写进第 6 节“在公有云上”一行。

第 10 节的第 4、5、6 条来自 Codex。
