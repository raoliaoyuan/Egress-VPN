# EVE-NG 实验：完整复现

在 EVE-NG 里用十七台 Linux 节点、真实的 WireGuard 和 Envoy 复现整个场景：现状（虚拟机自带隧道）、部署新方案、逐台迁移、回退、TLS、主备切换、“虚拟机拿不到凭证”，以及高可用与规模化（Egress 分片、多个网关单元加共享热备、两种数据面的对比、多台 VPN 服务器、凭证的规模化、经企业出口、逐台阻断）。

高可用与规模化这一部分的做法和结果单独写在 [docs/ha-scale-results.md](../../docs/ha-scale-results.md)（第一轮）和 [docs/ha-scale-results-2.md](../../docs/ha-scale-results-2.md)（第二轮），本文只列出怎么搭、怎么跑。

> 实验里的 Egress 是按“透明劫持”假设写的参考实现，不是真实的 Egress。其余组件用的都是仓库 `config/` 下的配置。

## 环境

- EVE-NG 主机要能免密 SSH 登录并免密 `sudo`，可以经一台跳板机。地址写在 `local.env` 里（不进版本库），参照 [local.env.example](local.env.example) 填写。
- 节点的起停在 EVE 主机上用 EVE 自己的代码和 `unl_wrapper` 完成，不登录网页接口。
- 节点镜像 `linux-egressvpn` 基于 EVE 上的 Debian 12 节点镜像（`linux-debian12`）用 `virt-customize` 定制。
- 每个节点的最后一块网卡接管理网（`pnet0`），操作机要能直连这个网段。
- 拓扑图里连到管理网的线默认隐藏：实验里有一个文本对象（MGMT 云图标下面的那段说明），带一段只在本实验生效的样式。在网页里删掉这段文字，连线就恢复显示。

- 压测工具 `labsrv`、`labload` 是 C 写的（[files/labsrv.c](files/labsrv.c)、[files/labload.c](files/labload.c)），阶段脚本在操作机上把它们编译成静态可执行文件再放到节点上，所以操作机要有 `cc` 和静态的 C 库。
- 节点不能直接上网。装 `iperf3` 和路由软件 FRR 时，脚本把操作机的 HTTP 代理（环境变量 `http_proxy`）经 SSH 反向隧道借给节点用。

实验文件是 `/opt/unetlab/labs/Egress-VPN.unl`。节点和网络的编号从 21 起，避开同一台 EVE 上其他实验已经占用的小编号：EVE 的网卡名、网桥名和控制台端口只由租户号和编号决定，不同实验用了相同编号就不能同时运行。

## 登录

- SSH：`ssh -i lab/eve-ng/state/lab_ed25519 lab@<管理网前缀>.81`（末段换成对应节点的）。`lab` 账户可以免口令 `sudo`，只接受这把实验专用密钥，不开口令登录。
- 控制台：在 EVE 网页里点节点，或 `telnet <EVE 主机> <32768 + 节点编号>`，直接以 `lab` 登录。

`state/` 目录保存实验专用的 SSH 密钥、WireGuard 密钥、证书和凭证（每台虚拟机在每个服务上一个令牌、每台虚拟机一张客户端证书），`local.env` 保存环境地址，两者都不进版本库。删掉 `state/` 就要重建镜像并重新部署。

`30-deploy-solution.sh` 会把网关层恢复成“一个单元、`gw-1` 主用 `gw-2` 备用”的基础形态，并撤掉数据面 B 和多台 VPN 服务器的东西；`20` 到 `71` 这些阶段都在基础形态上跑。`80` 之后是规模化形态，要回去就再执行一次 `30`。从多台 VPN 服务器的形态回规模化形态，也是先 `30` 再 `80`。

已有的实验要改拓扑（加节点、改核数和内存、改网卡接到哪个网络）时，改 [nodes.json](nodes.json) 后执行 `lab/eve-ng/lab-sync.sh`：它保留节点和网络在网页里的位置，只重启硬件有变化的节点。`lab-up.sh --recreate` 会按 `nodes.json` 里的位置重写整个实验文件。

EVE 主机关机后再开，先确认它已经启动并能登录，再执行 `lab-up.sh`。它只启动还没运行的节点；各节点上的服务都设了开机自启。

## 高可用与规模化（2026-11-21，2026-11-23）

实验从九个节点扩到十七个，网关层有四种形态，由脚本切换：

| 形态 | 网关层 | 建立它的脚本 |
|---|---|---|
| 基础形态 | 一个单元，`gw-1` 主用、`gw-2` 备用，`gw-3` 闲置 | `30-deploy-solution.sh` |
| 数据面 A 的规模化形态 | 两个单元加共享热备 `gw-3`，按地址块分 | `80-scale-a.sh` |
| 块 3 走数据面 B | 块 1、块 2 仍走数据面 A；块 3 的地址转换在 Egress 上，三台网关同时转发 | `85-dataplane-b.sh` |
| 多台 VPN 服务器 | 单元和热备同规模化形态；每台网关自己一对密钥，到两台 VPN 服务器各一条隧道，隧道里跑 BGP 加 BFD | `87-multi-server.sh` |

做法、数字和结论都在 [docs/ha-scale-results.md](../../docs/ha-scale-results.md) 和 [docs/ha-scale-results-2.md](../../docs/ha-scale-results-2.md)。这里只记和本目录有关的几件事：

- `20` 到 `71` 这些阶段在新拓扑的基础形态上全部通过，项数和下表相同；主备切换仍是断电约 3.9 秒、正常切换约 1.4 秒。
- 两台 Egress 的配置始终相同，部署 Egress 的公共函数同时处理两台。脚本里检查 Egress 的地方看的是 `egress-1`（平时负责三台真实虚拟机所在的块 1）。
- 虚拟机的默认网关现在是 `rtr-acc`，不再是 Egress。Egress 上“面向虚拟机的网卡”接的是 ACC-NET。
- Egress 和网关开机时执行 [files/tune.sh](files/tune.sh)：系统默认的连接跟踪表上限（1 GB 内存时 8192 条）在每秒几十条新连接时就会打满。
- 方案配置里加了 Envoy 的熔断阈值（`circuit_breakers`）：默认每个上游最多 1024 条连接，七层处理时每秒一百多个请求就会超过。
- VPN 服务器和内网服务之间多了一跳 `rtr-core`。只有一台服务器的形态下两个方向都是静态路由（由 `05-access.sh` 装的开机脚本加）；多台服务器的形态下换成 BGP，节点上的标记文件 `/etc/lab/ms-on` 让开机脚本不再加静态路由。
- 规模化形态下网关的健康检查是三项：Envoy 进程、够不够得着 Egress、承载着单元时隧道通不通（[files/gateway-tunnel-check.sh](files/gateway-tunnel-check.sh)）。每个单元在自己的地址块里留一个探测地址：单元 1 是 `100.64.3.253`，单元 2 是 `100.67.255.253`。
- nftables 里 `fwd`、`forward`、`snat` 是关键字，不能当链名。
- 实验主机的内核崩溃过四次（一个核空转，其余停机，所有节点连不上），原因没有查清，见第二轮结果的第 9 节。重置实验主机后执行 `lab-up.sh`，各种形态都能自己恢复；只有网关单元的主用位置可能不在第一顺位，用 `scale-lib.sh` 里的 `units_home` 挪回去。

## 结果（2026-11-20）

下表是加入“凭证不落到虚拟机”和“按凭证类型”之后，从现状开始把全部阶段完整重跑一遍的结果。

| 阶段 | 检查 | 结果 |
|---|---|---|
| 现状 | 10 项 | 全部通过 |
| 部署新方案 | 6 项 | 全部通过；部署后虚拟机的行为不变 |
| 逐项验证 | 29 项 | 全部通过 |
| 主备切换 | 21 项 | 全部通过，连续跑了两遍 |
| 凭证不落到虚拟机 | 40 项，另有 3 项对照 | 全部通过，3 项对照都成立 |
| 按凭证类型 | 34 项，另有 5 项对照 | 全部通过，5 项对照都成立 |

走到这个结果之前出过的问题：

- “逐项验证”最早有 1 项失败：伪造身份的对照实验用了“发送后立即半关闭连接”的方式，响应回来之前连接就被拆掉了。改成发送后保持连接后通过。
- “主备切换”连续多跑几遍后，内网访问会中断几分钟。原因是 Egress 到网关的空闲连接没有回收，见下面“实验中发现的两个问题”的第二条。修正后连续两遍都通过。
- “主备切换”有一次在备用网关上停 keepalived 时，隧道没有跟着停，两台网关抢了约 20 秒对端地址。keepalived 自己的停止通知那一次没有执行。现在由 systemd 在 keepalived 停止后再停一次隧道（[files/keepalived-stop.conf](files/keepalived-stop.conf)）。
- 连着跑两个凭证脚本时，第二个一开始就失败：脚本每换一次 Egress 的配置就重启一次 Envoy，超过了 systemd 默认的启动频率限制，服务停在失败状态。[files/envoy.service](files/envoy.service) 里取消了这个限制。
- **重跑时有几项抓包检查读到的是旧文件。** tcpdump 写出的文件属于 `tcpdump` 用户，节点上的系统不允许 root 覆盖 `/tmp` 下别人的文件，所以同一个文件名第二次抓包时写不进去，脚本读到的还是第一次的结果。受影响的是在不重启的节点上抓包的检查：现状里“Egress 只看到 WireGuard 的 UDP”和逐项验证里“Egress 能看到明文 TCP”。它们第一次执行时的结果是真实的，之后的重跑没有重新验证。现在所有抓包前都先删掉旧文件，期望为 0 的检查同时确认这次确实抓到了包。上表是修正之后重跑的结果。

要点：

- **现状复现了问题本身**：虚拟机经自己的隧道访问内网，内网看到各自的内网 IP，请求里没有凭证，服务认不出调用方；Egress 在虚拟机网卡上只抓到 WireGuard 的 UDP，没有任何去往内网服务的 TCP。
- **迁移后内网 IP 不变，凭证注入生效**：`vm-a` 迁移前后，内网服务看到的来源都是 `100.64.0.7`；迁移后内网服务从 Egress 注入的凭证认出了 `vm-a`。
- **新旧并存**：`vpn-server` 上每台虚拟机的 `/32` peer 和网关的 `/22` peer 同时存在时，未迁移的虚拟机不受影响。
- **旧密钥失效**：删除 peer 后，虚拟机用旧密钥重新拨号，握手次数为 0。迁移时虚拟机上的隧道配置和私钥也一并删除。
- **未登记的虚拟机被拦截**，登记后立即可用。
- **TLS**：Egress 向内网服务发起 TLS 时，在网关上抓包找不到凭证；不走 TLS 时，凭证在网关上以明文可见。
- **回退**：回退到旧方式、再次迁移，来源地址始终不变。
- **主备切换**：主用网关断电，从最后一次成功到恢复后第一次成功相隔约 3.8 到 3.9 秒（几遍的结果）；正常停掉主用的 keepalived，相隔约 1.4 秒。`vpn-server` 的配置在切换中没有改动，对端地址自动从 `203.0.113.11` 变成 `203.0.113.12`。探测间隔 0.2 秒、单次超时 1 秒，这两个数字的误差在 1 秒左右。

## 凭证不落到虚拟机

目标是虚拟机拿不到凭证。[phases/70-credential.sh](phases/70-credential.sh) 把虚拟机当成已被攻破，所有操作都以 root 在虚拟机上执行，逐条尝试凭证可能回到虚拟机的途径。

实验里的做法：

- **凭证按虚拟机、按服务区分**。每台虚拟机在每个服务上一个令牌，另有一张客户端证书。令牌和客户端私钥只部署到 Egress；服务端只保存令牌的 SHA-256，响应里返回的是“认出的调用方”，不是令牌。
- **只对指定的服务注入**。Egress 按“目的地址 + 端口 + Host”匹配，按来源地址选这台虚拟机的凭证。指定的服务是内网服务的 80、8081、8443、9443、6380 端口和公网站点的 80 端口（8081 和 6380 见下面“按凭证类型”），见 [files/gen-egress-envoy.py](files/gen-egress-envoy.py) 开头的 `SERVICES`。
- **三种形式**：80 端口是明文 HTTP 加令牌；8443 是 Egress 发起 TLS 后加令牌；9443 是 Egress 用这台虚拟机的客户端证书发起 TLS（mTLS），不加令牌。三种情况下虚拟机发的都是明文 HTTP。
- **其余**：虚拟机自带的同名请求头被覆盖或删除；TRACE 方法在 Egress 上拒绝；不开 Envoy 的管理接口；含凭证的配置和私钥只有 root 能读。

验证结果：

| 途径 | 检查 | 结果 |
|---|---|---|
| 让 Egress 把凭证发给别的站点 | 访问攻击者的站点、指定站点的其他端口；目的地址对但 Host 指向别处 | 对方收到的凭证头为 0；Host 不符时 Egress 返回 404，不转发 |
| 让服务把请求带回来 | TRACE 方法；服务回显全部请求头 | TRACE 被 Egress 拒绝（405）；走客户端证书时回显内容里没有任何凭证 |
| 冒充别的调用方 | `vm-b` 自带伪造的凭证头 | 服务认出的仍是 `vm-b` |
| 绕过 Egress | 虚拟机自己向 9443 发起 TLS | 失败 |
| 在线路上抓 | 在虚拟机自己的网卡上抓包；在网关上抓包 | 虚拟机一侧抓不到令牌；网关上看不到明文 HTTP |
| 在磁盘上找 | 扫描三台虚拟机的整个文件系统，找令牌样式的字符串，并把含私钥标记的文件与实验私钥比对摘要 | 都是 0。同样的扫描在 Egress 上能找到，说明扫描方法有效 |
| 从 Egress 上读 | 虚拟机经业务网、管理网登录 Egress | 都被拒绝 |

另外验证了**在 Egress 上摘掉一台虚拟机的凭证立刻生效**：`vm-c` 的请求仍能到达内网服务，但服务认不出调用方，走客户端证书的请求返回 503；其他虚拟机不受影响；放回之后恢复，令牌和证书都不用换。

三项对照：

- **不按目的地限定时凭证会被带走**。把 Egress 临时改成对任意目的地都注入（`--unscoped`），`vm-a` 向攻击者的站点发一个请求，对方就收到了令牌。恢复后同样的请求拿不到。
- **令牌的固有限制**。内网服务自己把请求头带回来时（实验里是 `/reflect`，代表调试接口、错误页），令牌回到了虚拟机。Egress 管不住服务端的行为，客户端证书没有这个问题。所以“虚拟机拿不到凭证”只有在服务认客户端证书（或请求签名）时才完全成立。
- **扫描方法有效**。见上表“在磁盘上找”。

没有验证的部分：

- 虚拟机被攻破后仍可以经 Egress 使用凭证，实验只验证了“拿不到”，没有涉及服务端的授权和审计。
- 虚拟机网段的源地址防伪造。凭证和内网 IP 都按来源地址选择，一台虚拟机冒用另一台的地址就同时拿到对方的两个身份。
- 实验里虚拟机和 Egress 接在同一个管理网上，这是实验环境的安排；“从管理面读不到”只检查了登录被拒绝和没有开管理接口。
- 请求签名、短期令牌、从凭证系统取凭证都没有做。

## 按凭证类型

真实的内网服务认的凭证三类都有：客户端证书、令牌、静态凭证。客户端证书的情况上一节已经验证（9443 端口）。[phases/71-credential-types.sh](phases/71-credential-types.sh) 验证另外两类，以及不走 HTTP 的服务。

实验里新增的东西：

- **服务端按来源地址限定**。内网服务的凭证表每行是“摘要 身份 允许的来源”：每台虚拟机的令牌和口令只接受从它自己的内网 IP 发来，共用账号只接受从网关的地址块 `100.64.0.0/22` 发来。这是默认做法，对照时临时去掉。
- **静态凭证（HTTP）**。内网服务的 8081 端口认 `Authorization: Basic`，账号 `svc-batch` 由所有虚拟机共用，Egress 注入。
- **不走 HTTP 的服务**。[files/resp-server.py](files/resp-server.py) 是 Redis 协议的最小实现，不是真的 Redis：6379 端口明文、要先用口令登录；6380 端口是 TLS，要求客户端证书，按证书认身份。
- **8080 端口代表“没有被 Egress 覆盖的入口”**。Egress 对它只做四层转发，虚拟机自己带的凭证会原样到达服务。脚本用它模拟“凭证已经泄露到某台机器上，被直接拿去用”。

验证结果：

| 凭证类型 | 检查 | 结果 |
|---|---|---|
| 令牌 | 不限定来源时，`vm-b` 和内网里另一台主机拿着 `vm-a` 的令牌 | 对照成立：都被服务当成 `vm-a` |
| 令牌 | 限定来源后，同样的做法 | 都被拒绝（来源不符）；三台虚拟机经 Egress 的正常访问不受影响 |
| 令牌 | `vm-a` 拿回自己的令牌直接用 | 来源和身份都还是它自己，没有多出权限 |
| 静态凭证（HTTP） | 虚拟机不带凭证访问 8081；自带伪造的 `Authorization`；访问攻击者站点的同一端口 | 服务认出共用账号；伪造的被覆盖；攻击者的站点收到 0 个 |
| 静态凭证（HTTP） | 服务回显请求头 | 对照成立：静态凭证同样回到了虚拟机 |
| 静态凭证（HTTP） | 轮换口令，只改服务端的凭证表和 Egress 的配置 | 三台虚拟机不做任何改动，访问照常；旧口令不再被接受 |
| 不走 HTTP，靠口令 | 让 Egress 上 Envoy 的 Redis 代理替虚拟机登录（`--redis-inject`） | 行不通：虚拟机收到 `upstream failure`，到网关的连接开头的 PROXY 头不带地址，内网服务没有收到任何包 |
| 不走 HTTP，靠口令 | 口令留在虚拟机里，Egress 按四层转发 | 能登录，来源是虚拟机的内网 IP；`vm-b` 和另一台主机拿着 `vm-a` 的口令都被拒绝 |
| 不走 HTTP，靠客户端证书 | 虚拟机不带任何凭证，发明文到 6380 | 服务收到 TLS，从证书认出各台虚拟机，来源是各自的内网 IP |
| 泄露之后摘掉 `vm-c` | 在 Egress 上摘掉 `vm-c`，它再拿之前得到的令牌从 8080 直接用 | 对照成立：仍被认作 `vm-c`。在服务端也作废这个令牌后被拒绝 |
| 泄露之后摘掉 `vm-c` | `vm-c` 拿泄露的共用凭证从 8080 直接用 | 对照成立：仍被接受，服务端没法只作废它一台。拿到内网里另一台主机上则被拒绝 |
| 收尾 | 再扫一遍三台虚拟机的文件系统 | 含令牌或静态凭证的文件数都是 0 |

从这些结果得出的结论：

- **令牌和静态凭证做不到“拿不到”，要靠服务端按来源地址限定来兜底。** 限定之后，泄露的凭证只能从原来那台虚拟机、经 Egress 没有覆盖的入口使用，身份和来源都还是它自己。
- **服务接受凭证的每个入口都要被 Egress 覆盖。** 实验里的 8080 就是没被覆盖的入口，上面两项对照都是经它做到的。真实环境里这类端口要么纳入七层处理，要么在 Egress 上拦掉。
- **不走 HTTP 的口令只能留在虚拟机里。** 本方案靠每条连接开头的 PROXY 头把虚拟机的身份带给网关；能替客户端登录的协议代理用的是自己的上游连接，带不了这个身份。服务改认客户端证书后，Egress 在四层代为出示即可，不需要看懂协议。
- **共用账号是最弱的一种。** 泄露后没法只作废一台，只能轮换；轮换本身不用动虚拟机。

这一节没有验证的部分：

- 不走 HTTP 的服务用的是最小实现，不是真的 Redis、MySQL 或 PostgreSQL。MySQL 和 PostgreSQL 的握手方式不同（先明文协商再升级到 TLS），Egress 在四层直接发起 TLS 的做法对它们是否适用没有验证。
- “服务端按来源地址限定”是在实验的回显服务里实现的，真实的内网服务能不能这样配置没有确认。
- 短期令牌没有做。

## 实验中发现的两个问题

### Egress 必须拒绝虚拟机访问网关所在的网段

网关无条件信任来自 Egress 的连接和其中的 PROXY 头。如果 Egress 对目的地址不加限制，虚拟机可以向网关的 15001 端口发起连接：这个连接被 Egress 透明劫持后原样转给网关，虚拟机只要在数据开头自带一个伪造的 PROXY 头，就能冒充任意一台已登记的虚拟机。

对照实验（`50-verify.sh` 的 D3 到 D5）：未登记的 `vm-c` 伪造 PROXY 头声称自己是 `vm-a`。Egress 上有拦截规则时没有任何响应；临时去掉这条规则后，内网服务把它当成了 `100.64.0.7`；恢复规则后再次无响应。

实验里的规则在 [files/egress.nft](files/egress.nft) 的 `guard` 链。真实的 Egress 需要有等价的限制。

### Egress 到网关的上游连接必须设空闲超时

Egress 对请求做七层处理时，每个请求都会在 Egress 到网关之间留下一条空闲连接，并一路占到内网服务上。实测：一台虚拟机发 10 个请求，Egress 到网关的连接多出 10 条，内网服务上也多出 10 条；四层转发的请求不会留下。

原因是 PROXY 头里带着下游连接的地址和端口，Envoy 给每条下游连接单独建一条上游连接，不同的下游连接之间不复用。下游连接关闭后，这条上游连接一直空着，Envoy 默认要等 1 小时才关。

实验里的表现：主备切换的探测每秒 5 个请求，连续跑几遍后，内网的回显服务被几百条空闲连接占满，新请求一进来就被关掉，看上去像是切换后内网不通。

修正：在 [config/egress/vpn-gateway-cluster.yaml](../../config/egress/vpn-gateway-cluster.yaml) 里给上游设了 10 秒的空闲超时。修正后 20 个请求留下的 20 条连接在 13 秒内全部回收。这个数值要按业务的长连接间隔调整；请求量大时，“请求速率 × 空闲超时”就是网关和内网服务上常驻的空闲连接数。

## 与方案文档的差别

- **主备切换的实现**：文档只写了“主备共用一对密钥，同一时刻只启动一台”。实验用 keepalived 在两台网关之间漂移服务地址，并在当上主用时启动隧道、其余情况停掉隧道（[files/keepalived.conf](files/keepalived.conf)、[files/gateway-notify.sh](files/gateway-notify.sh)）。
- **网关的映射表从空开始**：仓库的 `vpngw.nft` 里带一条示例记录，实验部署时去掉了它，记录全部由脚本登记。
- **网关入口过滤**：实验加了一条规则，15001 端口只接受 Egress 的地址（[files/gateway-filter.nft](files/gateway-filter.nft)）。文档里把这一点写成了要求，仓库没有给出配置。
- **凭证的处理**：文档把“凭证不落到虚拟机”的控制点和各类凭证要落实的事写成了要求。实验里的实现都在 Egress 的参考实现（[files/gen-egress-envoy.py](files/gen-egress-envoy.py)）和回显服务里，仓库的 `config/` 没有对应的配置，因为它取决于真实 Egress 现有的监听器结构。
- **过滤链按虚拟机逐台生成**：实验只有三台虚拟机，Egress 的配置里每台虚拟机、每个指定的服务端口各一条过滤链。虚拟机数量大时这种写法不可行，要换成动态下发或外部的凭证服务。
